# 동적 응답 코드 및 의도 평가

[English](../en/INTENT_BENCHMARK.md) · [한국어](INTENT_BENCHMARK.md) · [日本語](../ja/INTENT_BENCHMARK.md)

[English index](../en/README.md) · [한국어 색인](README.md) · [日本語索引](../ja/README.md)

후보 수는 전체 판단에 대한 하나의 공유 코드 너비를 판단합니다.

| 후보 수 | 코드 | 병렬 폭 |
| --- | --- | ---: |
| 2–26 | 에이, 비, …, 지 | 1 |
| 27–676 | AA, AB, …, ZZ | 2 |
| 677–17,576 | AAA, AAB, …, ZZZ | 3 |
| 17,577 and above | AAAA, AAAB, …; 필요에 따라 다시 연장 | 4 or more |

후보 수만큼만 코드가 사용됩니다. 예를 들어,  77 후보자는 AA–CY를 사용하고,  60는 AA–CH를 사용합니다. 알파벳에 따른 후보자 수 상한선은 없습니다. 코드 너비 산술은 카운트가 `usize` 제한에 접근할 때 오버플로를 방지합니다. 실제 요청은 평가해야 하는 응답 접두사를 포함하여 주소 지정 가능한 메모리와 모델의 컨텍스트에 의해 제한됩니다.

<a id="probability-contract"></a>
## 확률 계약

A-Z 경로는 정확한 프롬프트 및 단일 토큰 채점 동작을 유지합니다. 26 후보 이상에서는 판단의 모든 코드가 동일한 문자 너비를 갖습니다. 모델 템플릿은 해당 너비를 명시적으로 지시합니다. 후보 이름, 순서 및 의미론적 결과 ID는 변경되지 않습니다. 코드 회전은 실제 후보 수를 모듈로로 작동합니다.

토크나이저는 AA를 하나의 토큰 또는 여러 토큰으로 인코딩할 수 있습니다. 백엔드는 실제 보조 경계에서 각각의 완전한 연속성을 확인하고 경계 재토큰화, 중복 토큰 경로 및 다른 토큰 경로 앞에 붙는 모든 토큰 경로를 거부합니다. 각 표준 토큰 경로에 대해 자동 회귀 방식으로 점수를 매깁니다.

`log P(code | prompt) = sum(log P(next token | prompt, preceding code tokens))`

각 용어는 전체 어휘 분모를 사용합니다. 이러한 분리된 코드 확률의 합은 `candidate_mass`입니다. 전체 후보 세트에 대해 정규화하면 `option_probability`가 생성됩니다. 이는 첫 번째 문자 확률도 아니고 토큰 확률의 평균도 아닙니다. 동일한 텍스트의 대체 토큰화를 합산하지 않으며 보정된 정확성 확률을 주장하지 않습니다.

각 고유 코드 토큰 접두사는 한 번 평가됩니다. 이 판단 내에서 정확한 완전한 사전 충전 배치를 재사용할 수 있습니다. 각 분기는 원래 프롬프트와 자체 코드 접두사에서 시작됩니다. 생성된 가지가 다른 가지를 오염시키는 것은 허용되지 않습니다. KV 상태는 실패를 포함하여 시퀀스 채점 전후에 지워집니다. 이 경로에서는 후보자 명단이나 그룹 토너먼트가 사용되지 않습니다.

시퀀스 응답은 `scoring_method: code_sequence_conditional_softmax_v1`를 사용합니다. 각 점수에는 `token_ids`가 포함됩니다. `token_id`는 단일 토큰 경로의 유일한 토큰이고 다중 토큰 경로의 경우 `-1`입니다. 여기서 `raw_logit`는 결합 로그 확률을 저장합니다. `code_prefix_evaluations` 및 `code_evaluated_tokens` 보고서 네이티브는 모든 지점에서 작동합니다. `input_tokens`는 여전히 원래 프롬프트를 설명합니다. 응답 프롬프트 버전에는 `/fixed-width-code-sequences-v1`가 포함되어 있습니다.

다중 문자 코드는 출력 헤드, 스칼라 보정 또는 숨겨진 기능 내보내기 없이 완전한 증거로 새로운 실행 또는 접두사 재사용 실행을 지원합니다. 지원되지 않는 조합은 명시적으로 실패합니다. `encode_decision_sequences()` 및 `preflight()`는 완전한 후보 토큰 경로를 노출합니다. 이전 스칼라 토큰 내보내기는 광범위한 후보를 거부합니다. 단일 토큰 보정, 교육/내보내기 및 합의 워크플로는 기존 증거 계약을 유지합니다.

<a id="preparation-and-kv-caching"></a>
## 준비 및 KV 캐싱

`AA` 및 `AAA` 코드를 포함하여 정확한 프롬프트 준비 및 후보 토큰 경로를 캐시하려면 상주 백엔드에서 `PreparationCacheConfig`를 활성화합니다. 모든 코드 너비는 기존 바이트/항목 예산을 공유합니다. 상태 또는 스키마를 변경하면 프롬프트 누락이 발생하지만 호환 가능한 응답 경계 매핑을 계속 재사용할 수 있습니다. 캐시 항목에는 예측이 아닌 토큰이 포함됩니다. 실패한 준비는 저장되지 않습니다.

`ExecutionMode::PrefixReuse`를 선택하고 `backend.shared_state(state)`를 사용하여 하나의 불변 상태에서 호출 전반에 걸쳐 정확하고 완전한 사전 채우기 배치를 재사용합니다. 세션은 다른 판단 스키마를 수신할 수 있습니다. 일반 `decide()` 호출은 KV 격리 상태로 유지됩니다. 세션 생성, 오류 및 삭제는 KV를 삭제합니다. 지점 채점에서는 항상 원래 프롬프트와 지점 자체 접두사를 사용합니다. `reused_prefix_tokens`는 루트 프롬프트 재사용을 보고합니다. `code_evaluated_tokens`에는 모든 지점 작업이 포함됩니다.

캐시 비교 하네스는 동일한 고정 400 전체 레이블 요청, 사례당 첫 번째 호출 1회, 즉시 반복 3회, 전역 워밍업 2회를 사용합니다.

```sh
cargo run --release --offline --features llama --example measure_intent_cache -- \
  --model models/gemma-4-E2B-it-Q8_0.gguf \
  --input results/intent-wide-20260923/prepared/requests.jsonl \
  --output results/cache-session --mode session-cached
```

각 모드에 대해 새 출력 디렉터리(`fresh-uncached`, `fresh-cached` 또는 `session-cached`)를 사용합니다. 마지막 모드는 사례당 하나의 세션을 생성합니다. 보고서는 실제 준비 히트와 네이티브 재사용을 별도로 기록합니다. 핫 반복만으로는 캐시 적중을 증명할 수 없습니다. 타이밍에는 모델 로딩, 직렬화 및 세션 구성이 제외됩니다. 이는 새로운 발화 속도가 아니라 반복되는 동일한 호출을 측정합니다.

<a id="measured-repeated-request-cache-behavior"></a>
### 측정된 반복 요청 캐시 동작

RTX 3080/WSL2 호스트에서 실행되는 로컬 Gemma 4 E2B Q8_0은 동일한 고정된 200 영어 및 200 한국어 전체 레이블 요청을 사용했습니다. 각 사례에는 첫 번째 통화가 1회 있었고 즉시 반복 통화가 3회 있었습니다. 표는 각 사례의 반복 시간의 중앙값을 제공한 다음 200 사례 전체의 중앙값을 제공합니다. 모델 로딩, 세션 구성 및 직렬화는 제외됩니다. 기준선은 와이드 코드 경로에 준비 적중이 0인 이전 고정 빌드입니다. 따라서 소스 해시가 다릅니다.

| 모드 | BANKING77 / MASSIVE warm p50 ms | 프롬프트 적중 / 반복 1,200회 | KV 재사용 호출 / 재사용 토큰 |
| --- | ---: | ---: | ---: |
| 이전에 캐시되지 않은 기준선 | 138.70 / 103.61 | 0 | 0 / 0 |
| 준비 캐시로 fresh | 131.91 / 97.85 | 1,200 | 0 / 0 |
| 준비 캐시가 있는 동일 상태 세션 | 26.22 / 28.82 | 1,200 | 1,200 / 768,000 |

저장된 모든 예측, 점수, 후보 집단 및 정책 선택은 기준선과 정확히 일치했습니다. 추론 오류나 잘림이 발생하지 않았습니다. 측정된 세션 개선 사항은 변경 불가능한 상태에서 반복되는 동일한 질문에 적용됩니다. 준비 히트만으로는 이를 설명하지 못했습니다. 새로 캐시된 모드에는 KV 재사용이 없었고, 세션 모드에서는 460,800가 영어를 재사용했고 307,200는 한국어 접두사 토큰을 재사용했습니다. gitignored 로컬 소스 보고서는 `results/intent-cache-20260923-210112/REPORT.md`입니다.

<a id="banking77-and-massive-evaluation"></a>
## BANKING77 및 MASSIVE 평가

고정 테스트 샘플에는 200 영어 BANKING77 발화와 200 한국어 MASSIVE 발화가 포함되어 있습니다. RTX 3060 12 GiB 호스트의 Gemma 4 E2B Q8_0, E4B Q8_0 및 E4B Q4_K_M과 Qwen3-8B Q8_0에서 동일한 샘플이 사용됩니다. 모든 공식 77 또는 60 라벨은 모든 해당 요청에 표시됩니다. 원시 발화 텍스트만 상태에 들어갑니다. 골드 라벨, 시나리오, 주석 및 판단은 추론 범위를 벗어납니다.

샘플링은 데이터 세트별로 독립적으로 시드 `20260923`로 교체하지 않고 균일한 후 소스 순서로 복원됩니다. BANKING77의 샘플은 73 골드 클래스를 나타냅니다. MASSIVE의 샘플은 50를 나타냅니다. 전체 한국어 테스트 분할에는 `cooking_query` 예제가 없지만 해당 공식 클래스는 여전히 후보로 남아 있습니다. 지침은 BANKING77의 경우 영어이고 MASSIVE의 경우 한국어입니다. 판단 기준은 밑줄이 공백으로 대체된 원래 영어 레이블 이름을 사용합니다. 훈련, 검색, 골드 기반 후보 선택 또는 테스트 기반 프롬프트 조정이 수행되지 않습니다.

출처: [BANKING77 / PolyAI](https://github.com/PolyAI-LDN/task-specific-datasets) 및 [MASSIVE / Amazon](https://huggingface.co/datasets/AmazonScience/massive), 둘 다 CC BY 4.0. MASSIVE의 Korean Parquet는 개정판 `6e31162aba58a715666d3791566f42afdcfa62b2`에 고정되어 있습니다. 원시 파일 해시, 선택한 행 인덱스, 레이블 및 추론 요청은 로컬 결과 매니페스트에 유지됩니다.

`l2s1-tools evaluate-intents-wide`는 전체 라벨 실험을 준비, 실행 및 설명합니다. 이전 `l2s1-tools evaluate-intents` 명령은 별도의 26 후보 엔진 토너먼트 기준선을 유지합니다. 해당 결과는 단일 판단 전체 레이블 추론으로 레이블을 다시 지정해서는 안 됩니다.

결과, 정확한 명령, 빌드/테스트 로그 및 고정된 소스는 `results/intent-wide-20260923/`에 유지됩니다. 이전에 그룹화된 기준선은 `results/intent200-20260923/`에 유지됩니다. 각 정답률은 판단 보류 이전의 모든 200 예제를 사용합니다. 수락된 판단의 정답률, 수락률, 잘못된 답변 및 대기 시간은 별도로 보고됩니다. 이 샘플은 전체 데이터 세트 리더보드 결과가 아닙니다.

<a id="measured-results"></a>
## 측정 결과

4개의 원래 구성과 별도의 Gemma 4 26B 실행으로 추론 오류나 잘림 없이 200 행 하위 집합이 모두 완료되었습니다. 모든 요청에는 전체 공식 라벨 세트가 포함되었습니다.

| 모델 | BANKING77 영어 | MASSIVE 한국어 | 영어 / 한국어 p50 ms |
| --- | ---: | ---: | ---: |
| Gemma 4 E2B Q8_0 | 123/200 (61.5%) | 103/200 (51.5%) | 214.15 / 157.52 |
| Gemma 4 E4B Q8_0 | 130/200 (65.0%) | 143/200 (71.5%) | 371.72 / 277.05 |
| Gemma 4 E4B Q4_K_M | 130/200 (65.0%) | 138/200 (69.0%) | 383.61 / 287.00 |
| Gemma 4 26B A4B UD-Q4_K_M † | 152/200 (76.0%) | 156/200 (78.0%) | 2880.52 / 2134.52 |
| Qwen3-8B Q8_0 | 111/200 (55.5%) | 98/200 (49.0%) | 877.64 / 593.45 |

† 26B 결과는 18 CPU 전문가 레이어, 8개 스레드, 컨텍스트 8192 및 배치 256로 실행되는 별도의 RTX 3060입니다. 그 시간은 첫 번째 호출 중앙값입니다. 기본 정책에서는 191/200 영어 판단(148 맞음,  43 틀림)과 198/200 한국어 판단(156 맞음,  42 틀림)을 허용했습니다. 사례당 한 번의 즉시 반복 호출로 669.15/656.70 ms p50을 측정했으며 모든 400 사례에 대한 완전한 증거를 보존했습니다. 이 반복은 새로운 발화에 대한 추론 속도가 아닌 정확한 요청-로컬 캐시 재사용을 측정합니다. 별도의 배치 및 평가자 설정으로 인해 원래 4개 행과의 제어된 대기 시간 비교가 방지됩니다. 로컬의 gitignored 보고서는 `results/gemma26-offload-20260923-211926/REPORT.md`입니다.

이러한 Gemma 체크포인트는 사용된 모든 두 글자 코드를 하나의 토큰으로 인코딩합니다. Qwen3-8B는 4개의 BANKING77 코드와 2개의 MASSIVE 코드에 대해 2개의 토큰을 사용하며 각각 3개와 2개의 네이티브 접두사 평가가 필요합니다. 별도의 677 후보 Gemma GPU 테스트에서는 새로운 교사 강제에 대한 공동 로그 확률 차이가 0인 진정한 2토큰 `AAB`를 포함하여 3문자 코드의 점수를 매겼습니다. 231 항목 레거시 A–Z JevBench 재생은 모든 결과와 확률을 보존했습니다. 기본 테스트는 53/53를 통과했습니다. 라마 기능 모음은 19를 무시하고 63를 통과했습니다. 그런 다음 두 개의 대상 실제 모델 CUDA 테스트가 실행되어 통과되었습니다.

전체 보고서(로컬 아티팩트: `results/intent-wide-20260923/REPORT.md`, 커밋되지 않음)에는 원시 정답률, 허용된 오류, 수락률, 신뢰도 지표, 대기 시간 및 불변의 증거가 기록됩니다.

<a id="qwen-diagnosis"></a>
## Qwen 진단

탐색적 쌍대 대조 실험은 영어 입력 200개와 라벨 의미를 유지하면서 표시 순서와 코드 배정을 38칸 회전했습니다. 정답 수는 111/200에서 107/200로 바뀌었고 **83/200개의 예측 의미가 달라졌습니다**. 정답 23개가 오답으로, 오답 19개가 정답으로 바뀌었습니다. 이는 표시 순서·코드에 대한 상당한 민감성을 보여 주지만, 순서의 영향과 코드의 사전 편향을 분리하지는 않습니다. 회전 실험 점수는 진단용이며 원래 벤치마크를 대체하지 않습니다.

최소한 90%의 후보 신뢰도에서 원래 Qwen 실행에는 163 영어 예측 중 58 오류가 있었고 160 한국어 예측 중 68가 있었습니다. 2개의 토큰 골드 코드는 14 영어 예제에서만 발생했습니다. 대부분의 89 영어 오류는 단일 토큰 골드 코드에서도 발생했습니다. 토큰 길이만으로는 오류를 설명할 수 없습니다. 현재 라벨 이름만 사용하는 제로샷 설정에서는 세분화된 라벨 의미, 프리젠테이션 효과 및 신뢰도 보정이 별도의 개선 목표로 남아 있습니다. 수정된 프롬프트 또는 보정은 개발/보정 데이터에서 선택하고 별도의 손대지 않은 테스트 세트에서 평가되어야 합니다.
