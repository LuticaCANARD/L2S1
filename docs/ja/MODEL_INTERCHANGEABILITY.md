# L2S1 でのモデルの互換性

[English](../en/MODEL_INTERCHANGEABILITY.md) · [한국어](../ko/MODEL_INTERCHANGEABILITY.md) · [日本語](MODEL_INTERCHANGEABILITY.md)

[English index](../en/README.md) · [한국어 색인](../ko/README.md) · [日本語索引](README.md)

L2S1 は、互換性のあるローカル GGUF モデルを置き換えながら、アプリケーション 判断 コントラクトを維持します。 ID と 事前検証 は互換性を説明します。品質としきい値の適合性を確保するには、依然としてラベル付きのワークロードが必要です。

<a id="inspect-validate-run"></a>
## 検査、検証、実行

CPU の場合は `llama` フィーチャー、CUDA の場合は `llama-cuda` フィーチャーを使用してビルドします。 sys 依存関係は、llama.cpp ソースとライブラリに一致するものをビルドします。例ではコンパイルされたバイナリを使用します。

```sh
l2s1 --model models/SmolLM2-135M-Instruct-Q8_0.gguf --inspect
l2s1 --model models/SmolLM2-135M-Instruct-Q8_0.gguf \
  --input examples/warehouse.json --preflight
l2s1 --model models/SmolLM2-135M-Instruct-Q8_0.gguf \
  --input examples/warehouse.json --diagnostics
```

`LlamaBackend::inspect()` レポート チェックポイント SHA-256 (GGUF トークナイザーを含む)、埋め込みテンプレート ハッシュ、有効なプロンプト プロファイル/バージョン、ブリッジ/ランタイム ビルド ハッシュ、ロードされたラマ/ggml ライブラリ コンテンツ ハッシュ、アダプター/ヘッド ハッシュ、デバイスおよびコンピューティング構成。 チェックポイント およびロードされたライブラリのハッシュは、バックエンド の登録時に 1 回計算されます。したがって、スタートアップは完全な チェックポイント を読み取ります。最適化されたビルドをお勧めします。登録されたウェイト/アダプター/ランタイム ファイルは、使用中ずっと不変の状態に保ちます。この ID はコンテンツの出自であり、署名やファイルの同時変更に対する保護ではありません。 GPU ドライバー、ファームウェア、およびオペレーティング システムの ID はフィンガープリントされません。 CPU デバイス ラベルは、一意のプロセッサー モデルではなく、CPU バックエンド を識別します。構成が一致しても、すべての物理マシンで同一の動作が確立されるわけではありません。

現在、ロードされたライブラリの検出には Linux のダイナミック ローダーが使用されています。検証済みのランタイム検出が利用できない場合、ネイティブ バックエンド は明示的に失敗します。純粋な Rust スコアリング、校正 およびワーカー モジュールには Linux または llama.cpp は必要ありません。ランタイム ビルド ハッシュは、bridge/scoring/prompt/校正 ソース、依存関係ロックファイル、Jinja ソース、リンクされたコア ライブラリ、コンパイルされたブリッジ アーカイブ (推移的ヘッダーと C++ コンパイルを含む)、target/profile/Rust フラグ、およびコンパイラー バージョンをバインドします。ロードされたライブラリのハッシュは、動的にロードされる ggml デバイス バックエンドもカバーします。

`preflight()` は、推論と同じモデルにバインドされた準備を使用します。リクエストの構造、実行サポート、アクティブなアーティファクト、コンテキストの長さ、実際の応答境界での安定した候補の継続をチェックします。 26 までの候補は、既存の単一トークン マッピングを使用します。より大きなセットは固定幅の大文字コードを使用し、スカラー `candidate_token_ids` の代わりに `candidate_token_sequences` を返します。トークン シーケンスは一意であり、プレフィックスのないものである必要があります。これらの判断は、出力ヘッド、スカラー 校正、または機能エクスポートを使用せずに、完全な証拠を備えたフレッシュまたはプレフィックス再利用の実行をサポートします。 `encode_decision_sequences()` は完全なパスを公開します。古いスカラー エクスポート API はワイド コードを明示的に拒否します。 [シーケンス スコアリング契約](INTENT_BENCHMARK.md)を参照してください。 事前検証 は、推論なしでトークン数、候補マッピング、およびプロンプト トークン フィンガープリントを返します。機能フラグはメタデータに基づいており、モデルの品質や数値的等価性を保証するものではありません。ハイブリッド/リカレント モデルは並列実行を拒否します。プレフィックスの再利用は明示的にフレッシュに戻ります。状態の復元は、完全な証拠を転送する明示的なシリアル モードとして利用できます。ロードされた ヘッド は、既存のフレッシュのみ/デバイス/コンピューティング制限を引き続き適用します。

既存の `DecisionBackend::decide()` と応答 JSON は引き続き使用できます。 `decide_detailed()` は、モデル ID、判断 ごとの要求/有効な実行、フォールバック理由、証拠の起源、校正 ID、要求ローカル タイミング、およびスナップショット アカウンティングを含む別のエンベロープを追加します。生のプロンプトテキストは決して返されません。 事前検証 の準備/トークン ハッシュは推論タイミングの範囲外です。並列バッチの ネイティブ 時間は 1 回カウントされます。通常の 判断保留 は成功した結果のままです。詳細な障害では、無効なリクエスト、サポートされていない機能、互換性のないアーティファクト、コンテキスト オーバーフロー、無効なスコアの証拠、および ネイティブ 障害が区別されます。 CLI `--preflight`/`--diagnostics` は、標準出力でリクエスト ステージの失敗 JSON を返し、ゼロ以外の終了ステータスを返します。モデルの読み込みと不正な形式の JSON は、このエンベロープの前で失敗する可能性があります。

<a id="exact-evidence-and-policy"></a>
## 正確な証拠とポリシー

`ExactEvidence::from_logits()` は、完全な語彙ベクトルから検証済みの証拠を作成します。共有スコアラーは、正規化、バイナリ/選択/順序付き 解釈、タイ処理、および両方のアクセプタンス ゲートを所有します。元の f64 の合計順序が保持されます。証拠には、セマンティック ID、トークン ID、ネイティブ logits、語彙サイズ、および 全語彙 ログ ノーマライザーが保存されます。候補のみのスコア、部分的な上位 K の結果、および生成された数値推定では、逆シリアル化やパブリック フィールドのミューテーションを通じて、この正確な証拠タイプをインスタンス化することはできません。

全語彙 候補の確率質量 は、校正された確率から独立したままです。既存の出力ヘッドは、基本モデルのマス ゲートを保持し、同じポリシー スコアラーを使用します。証拠は、ネイティブ バックエンド の所有権と診断エンベロープによって、準備された 判断/モデルにバインドされます。これはポータブルな認証済み推論レシートではありません。

<a id="optional-execution-optimizations"></a>
## オプションの実行の最適化

全最適化は明示的に選びます。デフォルトは legacy プロンプト、fresh 実行、全根拠転送、準備キャッシュ無効です。アプリは反復・固定スキーマの処理を維持したり、リクエスト間でスキーマを変えたりできます。学習済み状態エンコーダーや新しいモデルは不要です。

<a id="bounded-preparation-reuse"></a>
### 制限された準備の再利用

```rust,ignore
backend.set_preparation_cache(l2s1::PreparationCacheConfig {
    max_entries: 128,
    max_bytes: 8 * 1024 * 1024,
});
let response = backend.decide(&request)?;
let cache_stats = backend.preparation_cache_stats();
backend.clear_preparation_cache();
```

バックエンドは、テキスト準備、画像プロンプト準備、候補対応の 3 つの FIFO キャッシュを所有します。全準備のキーは正確に直列化した状態と判断です。候補対応のキーは実際のアシスタント境界のテキストと候補数です。モデル・トークナイザー・テンプレートはバックエンドに属し、関連設定の変更でキャッシュを無効にします。質問・候補数・指示・状態が異なりミスした場合は通常の準備をします。成功した準備のみを保存し、予測・ネイティブ KV 状態は保存しません。返すトークンベクトルはコピーします。単一文字対応と複数文字トークン経路は同じ制限を共有し、広い対応は外側のベクトルと全トークン経路の割り当てを数えます。ヒットは実行モード・成果物の検査を迂回しません。

`max_entries` は各キャッシュに別々に適用され、合計は上限の 3 倍になり得ます。合計の `max_bytes` は半分をテキスト、1/4 ずつを画像プロンプトと候補対応に割り当てます。保持するキー・トークン割り当てとインライン項目を数え、アロケーター情報、余剰キュー容量、一時キー、返却コピーは対象外です。大きな項目は有用な項目を追い出さず保存を省略します。項目上限またはバイト上限が 0 なら保存を無効にします。`clear_preparation_cache()` は項目を消し、ヒット・ミス・追い出しカウンターを保持します。`set_preparation_cache()` は 3 キャッシュを置き換え、カウンターを初期化します。通常のリクエスト境界は準備トークンを保持し、ネイティブ KV は消します。

CLI に相当するのは `--preparation-cache-bytes 8388608 --preparation-cache-entries 128` です。バイトのデフォルトはゼロであるため、要求されるまでキャッシュは無効になります。 CLI の呼び出しごとに新しい バックエンド がロードされます。呼び出し間で再利用するには、常駐ライブラリ バックエンド またはワーカーが必要です。

<a id="compact-native-evidence-transfer"></a>
### コンパクト ネイティブ 証拠転送

```rust,ignore
backend.set_evidence_transfer(l2s1::EvidenceTransfer::Compact)?;
```

`--evidence-transfer compact` は、CLI で同じパスを選択します。 `Full` はデフォルトのままです。コンパクト モードは、C++ ブリッジで 全語彙 ログ ノーマライザーを計算し、そのノーマライザー、語彙サイズ、候補 logits ～ Rust のみを返します。 `candidate_mass` の意味は保持されます。分母を候補のみの正規化に置き換えることはありません。 ネイティブ logits は、ホスト上のボキャブラリー全体を引き続きカバーします。これにより、ボキャブラリー出力投影や llama.cpp のデバイスからホストへの作業ではなく、ホスト バッファーの Rust へのコピーが削除されます。同一の浮動小数点実装を想定するのではなく、実際のランタイムで数値デルタを比較します。

テキスト簡略化は、明示的共有状態セッションを含む fresh・prefix-reuse 実行に対応します。テキスト state-restore・parallel と学習済み出力ヘッドは拒否します。画像簡略化は単一トークン回答（最大 26 候補）の fresh・parallel に対応し、広い画像コードには fresh・全根拠が必要です。各画像シーケンスは独立した全語彙正規化値を保持します。転送モードはモデル・校正の識別に含み、簡略化応答で報告します。全モード JSON は互換性のため追加フィールドを省きます。校正の登録前にモードを選んでください。非互換モードに変更すると、他モードで学習した成果物を黙って再利用せず失敗します。

<a id="explicit-immutable-state-sessions"></a>
### 明示的な不変状態のセッション

```rust,ignore
backend.set_execution_mode(l2s1::ExecutionMode::PrefixReuse);
backend.set_prompt_layout(l2s1::PromptLayout::StateFirst);
{
    let mut session = backend.shared_state(state)?;
    let first = session.decide(first_questions)?;
    let next = session.decide(different_questions)?;
} // Native KV state is cleared here.
```

`SharedStateSession` は 1 つの バックエンド を排他的に借用し、1 つの不変 JSON 状態を所有します。各 `decide(Vec<Decision>)` 呼び出しでは、判断 ID、種類、命令、オプション数、および 判断基準 を変更できます。 ID は通話内で一意である必要があり、後の通話でも繰り返すことができます。モデル、アーティファクト、ポリシー、プロンプト構成は借用中に変更できません。各質問は引き続き、個別にコンパイルされたプロンプトを受け取ります。正確な共通トークン プレフィックスからの完全な事前入力バッチのみが再利用され、質問が以前の回答に反映されることはありません。

セッションでは、明示的に選択された `PrefixReuse` モードが必要で、リカレント/ハイブリッド メモリおよび出力ヘッドは拒否されます。選択したプロンプトのレイアウトと証拠転送モードが保持されます。状態優先レイアウトでは、質問が変更されると、より長い共通プレフィックスが公開される可能性がありますが、レイアウトを変更すると予測が変更される可能性があります。これは、明示的なセッション呼び出し全体で再利用される既存の因果デコーダーのプレフィックスであり、双方向状態エンコーダーや学習された小さな読み取り値 ヘッド ではありません。再利用は実際に一致するトークンに依存します。 1 つの短い質問を速くする必要はありません。

作成・呼び出し失敗・破棄でネイティブ KV を消します。失敗後も同じセッションは別の有効な呼び出しを受け付けます。通常の `DecisionBackend::decide()` はリクエスト境界で隔離され、セッションはその寿命の契約を変えません。各結果の `reused_prefix_tokens` は実際の再利用を示します。複数文字コードではルートプロンプト評価の再利用を示し、`code_evaluated_tokens` は全コード接頭辞分岐の復号トークンを数えます。広いコードは全根拠が必要です。借用中は `session.preparation_cache_stats()` と `session.take_timings()` でカウンターを確認できます。

<a id="scoped-scalar-calibration"></a>
## スコープ付きスカラー 校正

`ScalarCalibration::fit()` は、0.05 から 20 までの有界検索と、フィッティングが NLL を悪化させる場合の温度 1 フォールバックを使用して、校正 セット NLL によって正の温度をフィッティングします。 判断 の 3 種類すべてをサポートします。各アーティファクトは、完全なモデル/構成フィンガープリント、正確なタスク署名 (オプションの順序と 順序付き 値を含む)、ネイティブ スコア セマンティクス、校正 レコード ハッシュ、およびソース グループ ハッシュをバインドします。別のモデル、量子化、アダプター、テンプレート/プロファイル、コンピューティング設定、または実行モードは、リクエスト時にアーティファクトを拒否します。構成を変更しても、ロードされた 校正 はサイレントにドロップされません。

```sh
cargo run --release --offline --example fit_calibration -- fit-input.json task-temperature.json
l2s1 --model models/SmolLM2-135M-Instruct-Q8_0.gguf \
  --input examples/warehouse.json --calibration task-temperature.json --diagnostics
```

`fit-input.json` は `id`、`model`（確認の `identity`）、`decision`（正確な 1 判断）、`calibration` と独立した `held_out` 配列を含みます。各記録は `group`、候補順序の `raw_logits`、0 始まりの `correct_option` を含みます。正確なモデル・設定で測定した logits を渡してください。校正の学習器は数値だけで出典を確認できません。成果物を書き出す前に、重複する元グループ ID と評価候補数の不一致を拒否し、校正前後の評価 NLL・Brier を表示します。言い換えや候補変形は元の出典ごとに同じグループ ID にします。ID の完全一致検査は誤ったグループや近似重複を検出しません。

`evaluate_policy()` はさらに、測定されたベース 候補の確率質量 を受け入れ、採用率、採用された判断の正解率 (何も受け入れられない場合は null)、および指定された `DecisionPolicy` での最上位選択 正解率 をレポートします。ホールドアウト許容曲線にはいくつかのしきい値を使用します。近似メトリックは、テスト 正解率 ではなく、近似メトリックとして明示的にラベル付けされます。訓練された温度や普遍的に適した温度はバンドルされていません。

`register_calibration()`/`load_calibration()` でアーティファクトを登録します。 CLI は、繰り返される `--calibration` を受け入れます。タスク/ID ごとに最大 1 つのアーティファクトが受け入れられます。他のタスク ID では、ネイティブ スコアが維持されます。タスクの意味が変更された ID の照合は失敗します。生の logits と基本質量は保持されます。調整されたスコアとアーティファクト ID は明示的です。スカラー 校正 は、出力 ヘッド とスタックできません。 `clear_calibrations()` は明示的な削除操作です。

<a id="request-local-state-restoration"></a>
## ローカル状態の復元を要求する

```sh
l2s1 --model MODEL.gguf --input examples/warehouse.json \
  --prompt-layout state-first --execution-mode state-restore \
  --snapshot-limit-bytes 268435456 --diagnostics
```

状態の復元では、1 つのリクエスト内のすべての判断に共通する正確なプレフィックスが検索され、完全な事前入力バッチに切り捨てられます。 llama.cpp のシーケンス状態 API を使用して、そのプレフィックスを計算し、シーケンス状態全体を保存します。最初の 判断 は元のプリフィルから継続しています。後続の 判断 は、サフィックスを評価する前に、保存された状態をクリアして復元します。各回答には独立した logits があり、少なくとも最後のトークンは常に評価されます。最初の 判断 は、プレフィックスのプレフィルの料金を支払い、再利用されたトークンがゼロであることを報告します。後続の判断では、共有プレフィックスが報告されます。 `restores` 診断は実際の状態ロードをカウントするため、成功した N-判断 リクエストは N-1 リストアを報告します。単一の 判断 または短い共通プレフィックスのリクエストは新たに実行されます。

スナップショットは、ネイティブ 呼び出しから離れることはなく、リクエスト、エラー、コンテキストのサイズ変更、プロンプトの変更、またはアダプターの変更後にも存続します。スナップショット バッファは 1 つだけ存在します。そのサイズは、割り当て前に設定されたバイト制限と比較してチェックされます (デフォルトは 256 MiB、共通のプレフィックスが存在する場合、ゼロはバジェット フォールバックを強制します)。保存/復元のサポートが不足している場合、または予算を超過している場合は、明示的な新規フォールバックがトリガーされます。 ネイティブ デコード失敗はエラーのままです。診断では、スナップショットのバイト、保存/復元/プレフィル/サフィックスのウォールタイム、復元回数が明らかになります。これは、合計 RSS、GPU 割り当て、logits バッファー、または llama.cpp の内部スクラッチ メモリではなく、スナップショット バッファーを制限します。全プロセスのピーク RSS を個別に測定します。

これは、ハイブリッド メモリを含むシリアル状態復元です。これには完全な証拠の転送が必要ですが、ハイブリッド並列シーケンスや永続的な共有状態セッションは有効になりません。これは明示的な実行モードです。 `prefix-reuse` は KV ロールバックを引き続き使用し、リカレント/ハイブリッド モデルではフレッシュにフォールバックします。高速化は約束されていません。状態のコピーには再計算よりもコストがかかる可能性があります。導入前に、正確なモデル/構成を新たな実行と比較します。状態優先プロンプトも、変更された順序が実行モードとは関係なく予測を変更する可能性があるため、オプトインのままです。 [Bonsai RTX 3060 検証](benchmarks/bonsai-state-restore-20260925/REPORT.md) は、実際の状態の保存と復元を使用してハイブリッド パスを実行します。

<a id="bounded-ownership-and-scheduling"></a>
## 制限された所有権とスケジュール設定

`BackendWorker::spawn()` はバックエンドのファクトリー、キュー容量、直列化リクエストの最大バイト数、共有 `MemoryBudget`、正のモデルメモリ予約見積もりを受け取ります。ファクトリーは専用スレッド内に作成し、`LlamaBackend` は non-Send/non-Sync のままです。要求は所有スレッドで直列処理します。`submit()` は満杯のキューを即座に拒否し、受け入れた仕事に `DecisionTicket` を返します。`close()` は受け入れた仕事を完了し、スレッドを待ち、バックエンド・予約を解放します。チケット破棄は仕事を取り消しません。作成失敗・パニックは予約を解放し、停止したワーカーは切断を報告します。

```rust,ignore
let budget = l2s1::MemoryBudget::new(2 * 1024 * 1024 * 1024);
let mut worker = l2s1::BackendWorker::spawn(
    8, 1024 * 1024, &budget, 1024 * 1024 * 1024,
    move || l2s1::llama::LlamaBackend::load(
        &model_path, 2048, 256, 4, false, l2s1::DecisionPolicy::default()),
)?;
let response = worker.submit(request)?.wait()?;
worker.close()?;
```

`BackendWorker::spawn_batched()` は、ファクトリ引数の前に `BatchPolicy` を追加し、`BatchDecisionBackend` を必要とします。

```rust,ignore
let policy = l2s1::BatchPolicy {
    max_requests: 4,
    max_input_tokens: 8192,
    max_wait: std::time::Duration::from_millis(2),
};
let mut worker = l2s1::BackendWorker::spawn_batched(
    8, 1024 * 1024, &budget, 1024 * 1024 * 1024, policy,
    move || {
        let mut backend = l2s1::llama::LlamaBackend::load(
            &model_path, 2048, 256, 4, false, l2s1::DecisionPolicy::default())?;
        backend.set_execution_mode(l2s1::ExecutionMode::Parallel);
        backend.set_parallel_width(4)?;
        Ok(backend)
    },
)?;
```

トークンアドミッションでは、文字数やリクエスト数から推定するのではなく、実際のモデルの準備を使用し、すべての 判断 プロンプトを合計します。バッチごとのトークン制限を超えるリクエストは、独自のチケットを通じて失敗します。残りのバッチに適合しない有効なリクエストは、次のバッチを待ちます。結果は入力リクエストの順序とグループ化を保持します。 `max_wait` は、最初のリクエストの受付時間から予算を収集します。それは、推論の期限、厳しい 事前検証 時間制限、またはエンドツーエンドの遅延保証ではありません。待ち時間がゼロの場合は、追加のリクエストの収集がスキップされます。キューとシリアル化されたバイトの制限は引き続き適用されます。

`LlamaBackend` では、明示的に設定された `Parallel` モードのみが、許可されたリクエストを ネイティブ ウェーブにマージします。フレッシュ、プレフィックス再利用、状態復元モードはシリアルのままで、リクエストの分離が維持されます。 ネイティブ 並列エラーは、推論を再実行せずに影響を受けるバッチを失敗させます。パラレル モードでは、モデルの制限、追加の KV メモリ、および測定されたスコア ドリフト リスクが維持されます。トークンの入場と収集にも時間がかかります。バッチ処理だけでは、レイテンシの低下やスループットの向上は保証されません。

予約には、重み、KV/リカレント状態、出力、およびマージンのある ネイティブ スクラッチ スペースを含める必要があります。これらは、オペレーティング システムのメモリ制限ではなく、オペレータが指定した見積もりに基づいて許可を強制します。キューは、呼び出し元の既存の割り当てではなく、許可されたリクエスト数とシリアル化された入力サイズを制限します。クローズは、実行中の ネイティブ 呼び出しを待つことができます。強制キャンセルは行っておりません。モデルを変更するには、ワーカーをドレイン/クローズして別のワーカーを構築するか、両方に十分な予算を明示的に予約します。 HTTP サービス、リモート プロバイダー、永続的なクロスモデル キャッシュ、またはライブ ホットスワップ ポリシーは導入されていません。

<a id="validation-and-compatibility"></a>
## 検証と互換性

[検証ガイド](VERIFICATION.md)を参照してください。同じ適合性テストでは、コロンで区切られたモデル パスが受け入れられ、すべての結果の種類/マッピング、アーティファクト、障害、回復、スナップショット制限、最新スコアと最適化スコアがチェックされます。プレフィックスの再利用/状態復元では、既存の 0.02 確率/質量 判断基準 に加えて、変更されていない最上位の選択と受け入れられた結果が保持されます。並列実行には、[既知のバッチ形状ドリフト](PARALLEL_EXECUTION.md)があります。変更されていない等価性 判断基準 を個別に報告し、オプトインのままになります。

```sh
cargo test --locked --offline
cargo test --release --locked --offline --features llama
L2S1_CONFORMANCE_MODELS=MODEL_A.gguf:MODEL_B.gguf \
  L2S1_CONFORMANCE_REPORT=/tmp/conformance.json \
  cargo test --release --locked --offline --features llama \
  --test conformance -- --ignored --nocapture
```

[`examples/benchmark_optimizations.rs`](../../examples/benchmark_optimizations.rs) を使用して、オプションのパスをローカル モデルと比較します。

```sh
cargo run --release --locked --offline --features llama \
  --example benchmark_optimizations -- \
  --model MODEL_A.gguf --model MODEL_B.gguf \
  --output /tmp/l2s1-optimizations.json --repeats 3
```

出力は新しいものである必要があります。モデルごとに 1 つの バックエンド が常駐します。ハーネスは、ショート/ロングの合成ウェアハウス状態と 1/4/16 のサイクル選択、バイナリおよび 順序付き スキーマを質問し、パスの順序をローテーションし、測定された各パス/シナリオ/ラウンドの直前に時間制限のないウォームアップを 1 回実行します。完全な応答、ID、キャッシュ カウンタ、入力/再利用トークン、タイミングと最大確率/質量/logit の差が記録されます。キャッシュ/コンパクト パスはレガシーの新しいパスと比較されます。共有状態呼び出しは、状態優先のフレッシュ呼び出しと比較されます。質問ごとの償却時間は、個々のリクエストのレイテンシーではありません。同じウォームアップ入力により、準備が繰り返されます。新しい質問に対するキャッシュ ゲインは確立されません。このハーネスは、ワーカーのバッチ処理や、正解率 というラベルの付いたタスクを測定しません。

`ExecutionMode::StateRestore` および追加された `EvidenceTransfer` 構成では、ダウンストリームの完全一致と、手動で構築された Rust メタデータ構造体が必要に応じて更新される必要があります。デフォルトの完全転送 JSON では、追加された転送フィールドが省略されます。従来のプロンプト/新規実行のデフォルトと基本スコアのセマンティクスは保持されます。テスト フィクスチャとコントラクトの同等性は、本番環境 またはラベル付けされたワークロードの品質を確立しません。

<a id="cpugpu-placement"></a>
## CPU/GPU の配置

CUDA ロードは、`--gpu-layers N` および `--cpu-moe-layers N` を受け入れます。 1 つ目は、GPU レイヤーの配置を制限します。 2 つ目は、アテンションと共有ウェイトの通常の配置を維持しながら、最初の N MoE レイヤーのエキスパート ウェイトを CPU RAM に保持します。これらの設定は組み合わせることができます。これにより体重の滞留性が制御されます。 llama.cpp は、プレフィル中にホストの重みを使用した操作を CUDA にオフロードする場合があります。元の CUDA の読み込み動作を維持するには、両方を省略します。 CPU のみの読み込みでは、CUDA 配置リクエストが拒否されます。

```sh
l2s1 --model models/gemma-4-26B-A4B-it-UD-Q4_K_M.gguf --device cuda \
  --cpu-moe-layers 18 --context 8192 --batch 256 --threads 8 \
  --preparation-cache-bytes 67108864 --input request.json
```

Rust フィールドは、`ComputeOptions.gpu_layers: Option<u32>` および `cpu_moe_layers: u32` です。手動で構築された構造体では、従来のデフォルトの `None` および `0` を指定する必要があります。古い JSON は引き続き読み取り可能であり、デフォルトのシリアル化では両方のフィールドが省略されます。デフォルト以外の値は応答の計算メタデータとモデル ID に表示されるため、校正/ヘッド/ワーカー ID によって配置が区別されます。

CPU エキスパート分割には、MoE チェックポイント とそのレイヤー数以下の N が必要です。パターンは llama.cpp のエキスパート テンソル命名を使用し、ロードされたエンジンによって所有されたままになります。これは明示的な重みの配置であり、CUDA 割り当て失敗後の CPU フォールバックではありません。 ネイティブ ログは、実際の CPU/GPU バッファーを報告します。要求されたレイヤー数だけでは VRAM の予算を証明できません。 CPU RAM、KV、および計算バッファーも適合する必要があります。 RTX 3060 12 GiB では、コンテキスト 8192 およびバッチ 256 を持つ 26B Q4 チェックポイント が、14 でコンテキストの割り当てに失敗しました。 CPU エキスパート レイヤー; 18 レイヤーは、すべての 400 インテント ケース (200 BANKING77 英語および 200 MASSIVE 韓国語) を完了し、それぞれに最初の呼び出しと 1 つのキャッシュされた繰り返しが含まれます。すべての 400 キャッシュされた呼び出しは、完全な 判断 証拠を正確に保存しました。これにより、任意のコンテキストの長さや同時モデル インスタンスではなく、テストされた配置とコンテキストが検証されます。

量子化された CPU カーネルと GPU カーネルは、異なるスコアを生成する可能性があります。 CPU 常駐層を持つ Qwen3 0.6B Q8 プローブは、完全な CUDA (最大 0.028) に対する既存の 0.02 確率差 判断基準 を超えました。これは同等性の主張ではありません。意図した配置で 正解率 を評価します。準備とセッション キャッシュのチェックは、同じ配置での新しい推論と比較されます。

<a id="model-loading-and-peak-host-rss"></a>
## モデルの読み込みとピーク ホスト RSS

`--model-load-mode read` は、自動メモリ マッピングの代わりに、llama.cpp の通常の読み取り/アップロード パスを選択します。重みが既存の CPU および CUDA バッファーに到達する方法が変更されます。 チェックポイント、量子化、レイヤー分割、コンテキスト、または推論アルゴリズムは変更されません。 `auto` はデフォルトのままです。このオプションは、CLI、JSONL エバリュエーター、インテント キャッシュ ベンチマーク、および JevBench ハーネスで使用できます。

26B CPU/GPU 分割の場合は、配置コマンドに追加します。

```sh
l2s1 --model models/gemma-4-26B-A4B-it-UD-Q4_K_M.gguf --device cuda \
  --cpu-moe-layers 18 --model-load-mode read \
  --context 8192 --batch 256 --threads 8 --input request.json
```

Rust フィールドは `ComputeOptions.model_load_mode: ModelLoadMode` です。既存の Rust 構造体リテラルには `ModelLoadMode::Auto` を追加する必要があります。古い JSON は読み取り可能なままで、デフォルトのシリアル化ではフィールドが省略されます。明示的な `read` は、コンピューティング メタデータとモデル/アーティファクト ID に記録されます。元の ネイティブ エントリ ポイントは、外部参照呼び出し元の自動ロードを保持します。

プロセス RSS の削減は、物理メモリ需要の合計の削減と同じではありません。読み取りロードでは、割り当てられた バックエンド バッファ (潜在的には CUDA 固定ホスト メモリ) が使用されますが、マップされた重みはファイルにバックアップされたクリーンなページです。 OS ファイル キャッシュはプロセス RSS の外に残ります。対象のホストで負荷の高い RSS、定常推論 RSS、およびメモリ負荷を個別に測定します。すべての チェックポイント または CPU のみのデプロイメントで読み取りロードが優れていると想定しないでください。

1 台の RTX 3060 ホストで、同じ Gemma 4 26B A4B Q4 チェックポイントを使い、CPU expert 層を 18 層として、モードごとに 3 回、順序を交互に変えてウォームキャッシュから読み込みました。エンジンの最大 RSS の中央値は `auto` で 16.174 GiB、`read` で 9.349 GiB（42.2% 減）でした。読み込み直後の短時間 RSS の中央値は 10.332 対 9.334 GiB、読み込み時間は 10.361 対 13.931 秒でした。`read` 実行の全 231 JevBench 公開根拠オブジェクトは、以前の `auto` 実行と完全に一致しました。エンジン RSS ピーク時に採取したシステムの `MemAvailable` は `auto` で 28.903 GiB、`read` で 19.941 GiB のため、低いプロセス RSS は総物理メモリ需要が低いという根拠ではありません。これはローカル Linux/CUDA の測定で、Metal の結果や一般的な読み込み時間の保証ではありません。完全なローカルレポートとソースハッシュは、gitignore 対象の `results/gemma26-lowrss-20260923T135227Z/REPORT.md` にあります。

<a id="vision-optimization-components"></a>
## 視覚最適化コンポーネント

`--vision-optimized` (または `enable_vision_optimizations()` と `ComputeOptions::vision_optimized()`) は、4 つの独立した ネイティブ イメージ シーケンスと、準備キャッシュ、コンパクトな証拠、ダーティのみの KV クリアを組み合わせます。対応するプロジェクターと最大で 26 の回答オプションが必要です。キャッシュされた準備とコンパクトな証拠により、変更されていないコンピューティング構成でスコアが維持されます。並列/Flash Attention パスを組み合わせた場合、予測が変わる可能性があります。モデル、コンピューティング設定、およびハードウェアは、数値検証に使用される参照と一致する必要があります。以前の推論結果はキャッシュされません。
