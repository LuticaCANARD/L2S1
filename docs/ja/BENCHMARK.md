# ローカルモデル比較ベンチマーク

[English](../en/BENCHMARK.md) · [한국어](../ko/BENCHMARK.md) · [日本語](BENCHMARK.md)

[English index](../en/README.md) · [한국어 색인](../ko/README.md) · [日本語索引](README.md)

`decision-rules-v1` ベンチマークは、**12 リクエスト上の既存の GGUF チェックポイントと、36 ラベル付き判断** を比較します。ルールに従っている正確性、判断保留、繰り返し出力の一貫性、推論レイテンシーを測定します。モデルのダウンロードや配布は行いません。

デフォルトはレガシー v1 プロンプトです。オプションの v2 状態優先プロンプトとオプションのプレフィックスの再利用については、[SEMIF_ALGORITHM.md](SEMIF_ALGORITHM.md) に記載されています。比較用に別の出力ディレクトリを使用して、v2 の `--prompt-layout state-first` を渡し、次に `--execution-mode fresh` (デフォルト) または `--execution-mode prefix-reuse` を Rust ランナーに渡します。レポートには、要求されたモード、論理入力トークン、再利用されたプレフィックス トークン、および実際に評価されたトークンが記録されます。同じプロンプトのバージョン、モデル、デバイス、およびバッチ設定を比較します。プロンプトを変更すると、キャッシュの再利用とは関係なく、正解率 が変更される可能性があります。

`tests/fixtures/decision_benchmark.json` の英語の フィクスチャー は、2 つのドメインをカバーしています。

- 倉庫: 0、 6、 7、 24、 25、および 48 時間でのストレージの選択、コールド チェーン要件、および発送優先度。
- アクセス制御: ロールとスコープのマッピング、ブール値の編集権限、および 0、 1、 2、 3、および 4 試行における失敗試行のレビュー優先順位。

すべてのリクエストには、選択肢が 1 つ、バイナリが 1 つ、および 順序付き 判断 が 1 つあります。選択オプションの順序は異なります。 順序付き 値は、API の要求に応じてソートされたままになります。場合によっては、関係のないメモが含まれている場合もあります。予期される答えは、A/B/C トークンの位置に関係なく、セマンティック オプション ID です。通常の Rust テストは、シナリオ ルールからすべてのラベルを個別に再計算します。

これは、ルールに従う小規模な合成ベンチマークであり、一般的な推論、コーディング、多言語、安全性、または 本番環境-正解率 の評価ではありません。これらのラベルに合わせて調整したり、結果の数値を保留された 正解率 として表示したりしないでください。 `tests/native.rs` における実際のモデルの整合性テストは個別のままです。

<a id="run-the-five-model-matrix"></a>
## 5 つのモデルのマトリックスを実行する

前提条件: Rust 依存関係がすでにキャッシュされている、CMake、C++17 コンパイラー、およびローカルで取得されたチェックポイント。バンドルされた sys 依存関係により、固定された llama.cpp ソースが構築されます。 CUDA の実行には、さらに CUDA ツールキットが必要です。モデル パスは `tests/fixtures/benchmark_models.json` にリストされています。ランナーは、Hugging Face クライアント、アカウント、またはネットワーク リクエストを使用しません。モデルを入手する前に、個別のライセンスを確認してください。

```sh
cargo build --release --locked -p l2s1-tools
target/release/l2s1-tools benchmark-models \
  --device cpu cuda \
  --iterations 3 \
  --warmup 1
```

ランナーは、要求に応じて `--locked --offline` および CUDA 機能を使用して 1 回実行可能なリリース テストをビルドし、各モデルをハッシュし、一度に 1 つのモデル/デバイスを実行します。 CPU がデフォルトのデバイスです。 CUDA は明示的であり、サイレントに CPU にフォールバックすることはできません。 ネイティブ バックエンド は、実行全体で 1 つのロードされたモデルを再利用します。 Rust プロセスの起動、Cargo コンパイル、ロード、およびウォームアップは、定常状態のタイミングから除外されます。

サブセットを選択するか、設定を変更します。

```sh
target/release/l2s1-tools benchmark-models \
  --model gemma4 --model qwen3 \
  --device cuda \
  --iterations 10 --warmup 2 \
  --context 2048 --batch 256 --threads 4 \
  --min-top-probability 0.8 --min-candidate-mass 0.05 \
  --timeout 1800 \
  --output results/benchmark/my-comparison
```

`--iterations` は、すべての 12 リクエストにわたる完全な測定パスを意味します。 `--warmup` は、個別にタイミングを設定された 1 つの最初のリクエストに加えて、完全に除外されたパスを意味します。ケースの順序は、測定されたパス間で判断論的に回転します。繰り返しはタイミングと一貫性を特徴づけるのに役立ちます。独立した 正解率 サンプルの数は増加しません。

古いレポートが現在の結果と間違われないように、出力ディレクトリは新しいものである必要があります。デフォルトは、無視される `results/benchmark/` の下のタイムスタンプ付きディレクトリです。 `--timeout` は、ウォームアップを含め、各モデル/デバイスに個別に適用されます。ファイルの欠落、ネイティブ エラー、タイムアウトは、失敗した行として表示されたままになります。ランナーは他のモデルを続行し、実行が失敗した場合はゼロ以外の終了コードを返します。低い 正解率 は、テストの失敗ではなく、測定値として報告されます。

カスタム チェックポイントの場合は、`--manifest /path/to/models.json` を渡します。

```json
{
  "models": [
    {"id": "my-model", "path": "/absolute/path/to/chat-model.gguf"}
  ]
}
```

相対 チェックポイント パスは、カスタム マニフェストを含め、リポジトリ ルートに対して解決されます。 ID は、文字、数字、ハイフン、アンダースコアのみを含む一意の小文字の名前である必要があります。ベンチマークは バックエンド の自動プロンプト プロファイルを使用するため、モデルはそれぞれのテンプレートを通じて同じセマンティック タスクを受け取ります。テンプレート/トークンの数とモデルのサイズを比較します。

<a id="reports-and-metric-definitions"></a>
## レポートとメトリックの定義

各ディレクトリには、`summary.md`、`summary.json`、ビルド ログ、モデル/デバイスごとの JSON および ネイティブ ログが含まれます。 チェックポイント SHA256、フィクスチャー SHA256、実行可能 SHA256、利用可能なリポジトリ/llama.cpp リビジョン、デバイス、量子化 の説明、設定、ポリシー、個々のラベル、予測、確率、およびレイテンシーのサンプルが保持されます。生のローカル レポートにはローカル モデル パスを含めることができます。公開する前にレビューしてください。

| 指標 | 定義 |
| --- | --- |
| 採用率 | 受け入れられた判断 / すべての測定された判断 |
| 判断保留 レート | 判断保留された判断 / すべての慎重な判断 |
| 採用された判断の正解率 | 受け入れられた判断/受け入れられた判断を修正します。 `null` / `n/a` (何も受け入れられなかった場合) |
| 採用した正解 / 全体 | 承認された判断/すべての判断を修正します。判断保留は正解とはみなされない |
| 生トップ-1 正解率 | ポリシー 判断保留 より前の、ラベルに対する最高スコアのセマンティック オプション。同点カウントが正しくありません |
| 正しく受け入れられました/秒 | 受け入れられた正しい判断/測定された推論秒数 |
| 判断/秒 | 判断保留を含むすべての完了した判断/測定された推論秒数 |
| リクエスト p50/p95 | 完全な `decide` 呼び出しの最も近いランクのパーセンタイル。それぞれに 3 つの連続した判断が含まれます。 |
| 入力トークン/秒 | 処理した入力トークン / 推論秒数。生成トークン/秒とは別の指標 |
| 繰り返しの一貫性 | 受け入れられた出力と生のトップ - 1 の変更と、同じケースの最初のパス/判断 |

品質の数と分数は、ドメイン別および 判断 種類別にも表示されます。完全なサンプルにより、ケースごとの検査が可能になります。出力を繰り返すと、スコアが変化しても同じ選択されたオプションが維持される場合があります。このレポートは、ネイティブ スイートの確率/バッチ チェックに代わるものではありません。

読み込みと最初のリクエストは個別にレポートされます。タイミングには、迅速な準備、事前入力、logits 転送、およびスコアリングが含まれますが、JSON レポートのシリアル化は含まれません。 OS ページ キャッシュはフラッシュされません。ロード時間はコールドディスクでの測定値ではありません。フルコンテキスト容量、プロセス RSS、ピーク VRAM、および同時処理スループットは測定されません。意味のある比較を行うには、ハードウェア、量子化、コンテキスト、バッチ、スレッド数、ポリシーの一貫性を保つ必要があります。任意のハードウェア速度しきい値はありません。

<a id="test-the-benchmark-without-models"></a>
## モデルを使用せずにベンチマークをテストする

```sh
cargo test --locked --offline --test benchmark
cargo test --locked --offline -p l2s1-tools
```

これらは、フィクスチャー ラベルとメトリック分母を検証します。これには、同点と全禁止出力に加えて、マニフェスト検証と失敗保存レポートが含まれます。それらは実際の推論の正しさを証明するものではありません。

実際のモデルのベンチマークは、`tests/benchmark.rs` で無視された Rust テストです。直接実行することもできます。

```sh
SKID_MODEL=/absolute/path/to/model.gguf \
SKID_CUDA=1 \
SKID_BENCH_ITERATIONS=3 \
SKID_BENCH_WARMUP=1 \
SKID_BENCH_OUTPUT=results/benchmark/single-model.json \
  cargo test --release --locked --offline --features llama --test benchmark \
  native::model_decision_benchmark -- --exact --ignored --nocapture
```

直接実行では、`SKID_CONTEXT`、`SKID_BATCH`、`SKID_THREADS`、`SKID_MIN_TOP_PROBABILITY`、および `SKID_MIN_CANDIDATE_MASS` を受け入れます。 Rust ランナーは、チェックポイント ハッシュと比較テーブルを追加します。以前の `tests/performance.rs` は、単一の倉庫の例を繰り返し測定するために引き続き使用できます。
