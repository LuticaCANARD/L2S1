# 動的な応答コードと意図の評価

[English](../en/INTENT_BENCHMARK.md) · [한국어](../ko/INTENT_BENCHMARK.md) · [日本語](INTENT_BENCHMARK.md)

[English index](../en/README.md) · [한국어 색인](../ko/README.md) · [日本語索引](README.md)

候補数によって、判断 全体の 1 つの共有コード幅が決まります。

| 候補数 | コード | 並列幅 |
| --- | --- | ---: |
| 2–26 | A、B、…、Z | 1 |
| 27–676 | AA、AB、…、ZZ | 2 |
| 677–17,576 | AAA、AAB、…、ZZZ | 3 |
| 17,577 and above | ああああ、ああああ、…;必要に応じて再度延長する | 4 or more |

候補と同数のコードのみが使用されます。たとえば、 77 候補は AA–CY を使用し、 60 は AA–CH を使用します。アルファベット由来の候補者数の上限はありません。コード幅の演算により、カウントが `usize` 制限に近づいた場合のオーバーフローが回避されます。実際のリクエストは、アドレス指定可能なメモリと、評価する必要がある応答プレフィックスを含むモデルのコンテキストによって制限されたままになります。

<a id="probability-contract"></a>
## 確率契約

A ～ Z パスは、正確なプロンプトと単一トークンのスコアリング動作を保持します。 26 候補の上では、判断 内のすべてのコードの文字幅は同じです。モデル テンプレートはその幅を明示的に指示します。候補名、順序、およびセマンティック結果 ID は変更されません。コードローテーションは、実際の候補数を法として演算します。

トークナイザーは、AA を 1 つのトークンまたは複数のトークンとしてエンコードできます。 バックエンド は、実際のアシスタント境界で完全な継続をそれぞれチェックし、境界の再トークン化、重複したトークン パス、および別のトークン パスに接頭辞を付けるトークン パスを拒否します。各正規トークン パスを自己回帰的にスコア付けします。

`log P(code | prompt) = sum(log P(next token | prompt, preceding code tokens))`

各用語は完全な語彙の分母を使用します。これらの素なコード確率の合計は `candidate_mass` です。完全な候補セットを正規化すると、`option_probability` が生成されます。これは、最初の文字の確率でも、トークンの確率の平均でもありません。同じテキストの代替トークン化を合計するものではなく、調整された正しさの確率を主張するものでもありません。

個別のコードトークンプレフィックスはそれぞれ 1 回評価されます。正確に完全な事前充填バッチは、この 判断 内で再利用できます。各ブランチは、元のプロンプトと独自のコード プレフィックスから始まります。生成されたブランチが他のブランチを汚染することは許可されません。 KV 状態は、失敗を含むシーケンス スコアリングの前後でクリアされます。このパスでは、最終候補者リストやグループ トーナメントは使用されません。

シーケンス応答は `scoring_method: code_sequence_conditional_softmax_v1` を使用します。各スコアには `token_ids` が含まれます。 `token_id` は 1 トークン パスの唯一のトークンであり、マルチトークン パスのトークンは `-1` です。ここで、`raw_logit` には結合対数確率が格納されます。 `code_prefix_evaluations` および `code_evaluated_tokens` は、ネイティブ がすべてのブランチで機能することを報告します。 `input_tokens` は依然として元のプロンプトを説明しています。応答プロンプトのバージョンには `/fixed-width-code-sequences-v1` が含まれます。

マルチレターコードは、出力ヘッド、スカラー 校正、または隠し機能エクスポートなしで、完全な証拠を備えたフレッシュまたはプレフィックス再利用の実行をサポートします。サポートされていない組み合わせは明示的に失敗します。 `encode_decision_sequences()` および `preflight()` は、完全な候補トークン パスを公開します。古いスカラー トークンのエクスポートでは幅広い候補が拒否されます。シングルトークン 校正、トレーニング/エクスポート、およびコンセンサスのワークフローは、既存の証拠契約を保持します。

<a id="preparation-and-kv-caching"></a>
## 準備と KV キャッシュ

常駐 バックエンド で `PreparationCacheConfig` を有効にして、正確なプロンプト準備と候補トークン パス (`AA` および `AAA` コードを含む) をキャッシュします。すべてのコード幅は、既存のバイト/エントリ バジェットを共有します。状態またはスキーマを変更するとプロンプトミスが発生しますが、互換性のある回答境界マッピングを再利用できます。キャッシュ エントリには予測ではなくトークンが含まれます。失敗した準備は保存されません。

`ExecutionMode::PrefixReuse` を選択し、`backend.shared_state(state)` を使用して、1 つの不変状態の呼び出し全体で正確で完全な事前入力バッチを再利用します。セッションは異なる 判断 スキーマを受け取る場合があります。通常の `decide()` 呼び出しは KV 分離されたままになります。セッションの作成、エラー、ドロップ クリア KV。ブランチのスコアリングでは、常に元のプロンプトとブランチ独自のプレフィックスが使用されます。 `reused_prefix_tokens` は root プロンプトの再利用を報告します。 `code_evaluated_tokens` には、すべてのブランチ作業が含まれます。

キャッシュ比較ハーネスは、同じ凍結された 400 フルラベル リクエストを使用し、ケースごとに 1 回の最初の呼び出しと 3 回の即時繰り返しを、2 つのグローバル ウォームアップとともに使用します。

```sh
cargo run --release --offline --features llama --example measure_intent_cache -- \
  --model models/gemma-4-E2B-it-Q8_0.gguf \
  --input results/intent-wide-20260923/prepared/requests.jsonl \
  --output results/cache-session --mode session-cached
```

各モードに新しい出力ディレクトリを使用します: `fresh-uncached`、`fresh-cached`、または `session-cached`。最後のモードでは、ケースごとに 1 つのセッションが作成されます。レポートには、実際の準備ヒットと ネイティブ の再利用が個別に記録されます。ホットリピートだけではキャッシュヒットの証拠にはなりません。タイミングには、モデルの読み込み、シリアル化、セッションの構築は含まれません。これは、新規の発話速度ではなく、同じ通話の繰り返しを測定します。

<a id="measured-repeated-request-cache-behavior"></a>
### 測定された反復リクエストのキャッシュ動作

RTX 3080/WSL2 ホスト上で実行されるローカル Gemma 4 E2B Q8_0 は、同じ凍結された 200 英語および 200 韓国語のフルラベル リクエストを使用しました。各ケースには最初のコールが 1 回あり、すぐに再診が 3 回ありました。この表には、各ケースの繰り返し時間の中央値が示され、次に 200 ケース全体の中央値が示されます。モデルの読み込み、セッションの構築、シリアル化は含まれません。ベースラインは、ワイド コード パスに準備ヒットがゼロの、以前に凍結されたビルドです。したがって、ソースハッシュは異なります。

| モード | BANKING77 / MASSIVE warm p50 ms | プロンプトヒット / 1,200 反復 | KV 再利用呼び出し / 再利用トークン |
| --- | ---: | ---: | ---: |
| 以前のキャッシュされていないベースライン | 138.70 / 103.61 | 0 | 0 / 0 |
| 準備キャッシュを使用してfresh | 131.91 / 97.85 | 1,200 | 0 / 0 |
| 準備キャッシュを使用した同じ状態のセッション | 26.22 / 28.82 | 1,200 | 1,200 / 768,000 |

保存されたすべての予測、スコア、候補集団、および政策選択はベースラインと正確に一致しました。推論エラーや切り捨ては発生しませんでした。測定されたセッションの改善は、不変の状態で繰り返された同じ質問に適用されます。準備ヒットだけではこれは考慮されませんでした。フレッシュ キャッシュ モードでは KV の再利用がありませんでしたが、セッション モードでは、英語の 460,800 が再利用され、韓国語のプレフィックス トークンが再利用された 307,200 が記録されました。ローカルの gitignored ソース レポートは `results/intent-cache-20260923-210112/REPORT.md` です。

<a id="banking77-and-massive-evaluation"></a>
## BANKING77 および MASSIVE の評価

凍結されたテスト サンプルには、200 英語 BANKING77 発話と 200 韓国語 MASSIVE 発話が含まれています。同じサンプルが、RTX 3060 12 GiB ホスト上の Gemma 4 E2B Q8_0、E4B Q8_0、および E4B Q4_K_M、さらに Qwen3-8B Q8_0 によって使用されます。すべての公式 77 または 60 ラベルがそれぞれのリクエストに存在します。生の発話テキストのみが状態に入ります。ゴールドラベル、シナリオ、注釈、判断は推論の範囲外のままです。

サンプリングはシード `20260923` で置換することなく均一であり、データセットごとに個別に行われ、その後ソースの順序に復元されます。 BANKING77 のサンプルは、73 ゴールド クラスを表します。 MASSIVE のサンプルは 50 を表します。韓国語の完全なテスト分割には `cooking_query` の例はありませんが、その公式クラスは候補のままです。説明書はBANKING77は英語、MASSIVEは韓国語です。 判断基準 は、アンダースコアをスペースに置き換えた元の英語のラベル名を使用します。トレーニング、取得、ゴールドベースの候補選択、またはテスト主導のプロンプトチューニングは実行されません。

出典: [BANKING77 / PolyAI](https://github.com/PolyAI-LDN/task-specific-datasets) および [MASSIVE / Amazon](https://huggingface.co/datasets/AmazonScience/massive)、どちらも CC BY 4.0。 MASSIVE の韓国語 Parquetは、リビジョン `6e31162aba58a715666d3791566f42afdcfa62b2` に固定されています。未加工ファイルのハッシュ、選択された行インデックス、ラベル、および推論リクエストは、ローカルの結果マニフェストに保持されます。

`l2s1-tools evaluate-intents-wide` は、完全なラベル実験を準備、実行、再集計します。以前の `l2s1-tools evaluate-intents` コマンドは、別の 26-candidate-engine トーナメント ベースラインを保持します。その結果は、単一 判断 完全ラベル推論として再ラベルされてはなりません。

結果、正確なコマンド、ビルド/テスト ログ、および凍結されたソースは `results/intent-wide-20260923/` に保持されます。以前にグループ化されたベースラインは `results/intent200-20260923/` に保持されます。各 正解率 は、判断保留 より前のすべての 200 の例を使用します。 採用された判断の正解率、採用率、間違って受け入れられた回答と遅延は個別にレポートされます。これらのサンプルは、完全なデータセットのリーダーボード結果ではありません。

<a id="measured-results"></a>
## 測定結果

4 つの元の構成と個別の Gemma 4 26B の実行により、推論エラーや切り捨てが発生することなく、両方の 200 行サブセットが完了しました。すべてのリクエストには、公式ラベル セット全体が含まれていました。

| モデル | BANKING77 英語 | MASSIVE 韓国語 | 英語 / 韓国語 p50 ms |
| --- | ---: | ---: | ---: |
| Gemma 4 E2B Q8_0 | 123/200 (61.5%) | 103/200 (51.5%) | 214.15 / 157.52 |
| Gemma 4 E4B Q8_0 | 130/200 (65.0%) | 143/200 (71.5%) | 371.72 / 277.05 |
| Gemma 4 E4B Q4_K_M | 130/200 (65.0%) | 138/200 (69.0%) | 383.61 / 287.00 |
| Gemma 4 26B A4B UD-Q4_K_M † | 152/200 (76.0%) | 156/200 (78.0%) | 2880.52 / 2134.52 |
| Qwen3-8B Q8_0 | 111/200 (55.5%) | 98/200 (49.0%) | 877.64 / 593.45 |

† 26B の結果は、18 CPU エキスパート レイヤー、8 つのスレッド、コンテキスト 8192 およびバッチ 256 で実行された別の RTX 3060 です。その時間はファーストコールの中央値です。デフォルトのポリシーは、191/200 英語の判断 (148 が正しく、 43 が間違っている) と 198/200 韓国の判断 (156 が正しく、 42 が間違っている) を受け入れました。ケースごとに 1 回の即時反復コールで 669.15/656.70 ms p50 が測定され、すべての 400 ケースの完全な証拠が保存されました。この繰り返しは、新しい発話の推論速度ではなく、リクエストのローカル キャッシュの正確な再利用を測定します。配置とエバリュエーターの設定が別々であるため、元の 4 行との制御されたレイテンシの比較ができなくなります。そのローカルの gitignored レポートは `results/gemma26-offload-20260923-211926/REPORT.md` です。

これらの Gemma チェックポイントは、使用されるすべての 2 文字コードを 1 つのトークンとしてエンコードします。 Qwen3-8B は、4 つの BANKING77 コードと 2 つの MASSIVE コードに 2 つのトークンを使用し、それぞれ 3 つと 2 つの ネイティブ プレフィックス評価を必要とします。別の 677 候補 Gemma GPU テストでは、純粋に 2 トークンの `AAB` を含む 3 文字のコードがスコア付けされ、新しい教師の強制との結合対数確率の差は 0 でした。 231 アイテムのレガシー A-Z JevBench リプレイでは、すべての結果と確率が保存されていました。デフォルトのテストは 53/53 に合格しました。ラマ機能スイートは 63 を渡しましたが、19 は無視されました。次に、対象となる 2 つの実際のモデル CUDA テストが実行され、合格しました。

完全なレポート (ローカル アーティファクト: `results/intent-wide-20260923/REPORT.md`、コミットされていない) には、生の 正解率、受け入れられたエラー、採用率、信頼性メトリクス、レイテンシー、および不変の証拠が記録されます。

<a id="qwen-diagnosis"></a>
## Qwen 診断

探索的な対照実験では英語入力 200 件とラベルの意味を維持し、表示順序とコード割り当てを 38 個分ずらしました。正解数は 111/200 から 107/200 に変わり、**83/200 件で予測の意味が変化しました**。正解 23 件が不正解に、不正解 19 件が正解になりました。表示・コードに対する大きな感度を示しますが、順序の影響とコードの事前バイアスは分離していません。この結果は診断用で、元のベンチマークを置き換えません。

少なくとも 90% の候補の信頼度では、元の Qwen 実行には、163 英語予測の間に 58 エラーがあり、160 韓国語予測の間に 68 エラーがありました。 2 トークンのゴールド コードは、14 英語の例でのみ発生しました。 89 英語エラーのほとんどは、単一トークンのゴールド コードでも発生しました。トークンの長さだけではエラーを説明できません。現在のラベル名のみのゼロショット設定では、きめ細かいラベル セマンティクス、プレゼンテーション効果、信頼性 校正 が個別の改善目標として残されています。改訂されたプロンプトまたは 校正 は、開発/校正 データで選択し、別の未変更のテスト セットで評価する必要があります。

診断レポート (ローカル アーティファクト: `results/intent-wide-20260923/diagnostics/REPORT.md`、コミットされていない) には、例ごとのペアの予測とトークン長の遷移が含まれています。
