# 共有状態プレフィックスの再利用、質問の変更

[English](../../../en/benchmarks/shared-state-cache-20260925/REPORT.md) · [한국어](../../../ko/benchmarks/shared-state-cache-20260925/REPORT.md) · [日本語](REPORT.md)

[English index](../../../en/README.md) · [한국어 색인](../../../ko/README.md) · [日本語索引](../../README.md)

コミットされていない変更を含むコミット `72fdef3eabaae579d640cb7b51d18a29dc83791e` の現在の作業ツリーを使用して、RTX 3080 (コンピューティング機能 8.6) で 2026-09-25 を測定しました。リリース CUDA ビルドは `sm_86` をターゲットとしていました。どちらのモデルも、コンテキスト 2048、バッチ/ubatch 32、4 つの CPU スレッド、完全な証拠、および両方のパスで同じ状態優先プロンプトを使用しました。モデルのロードとチェックサムの検証は除外されました。

このレポートは、そのローカル スナップショットを記録します。これを含むプル リクエストは、後の `main` に基づいています。以下のタイミング数値は、その後のツリーでは取得されませんでした。

各パスは、通話ごとに 1 つの質問を受け取りました。 16 の質問には個別の ID と指示テキストがあったため、後の呼び出しでは、同一の完全なプロンプトを繰り返すことなく状態プレフィックスを再利用できました。短いウェアハウス状態と、200 無関係な `packing` 単語を含むバージョンがテストされました。条件ごとに 5 つの測定ラウンドで、それぞれ 1 回の時間制限なしのウォームアップが行われました。パスの順序はラウンド間で交互になります。以下の時間は、セッションの作成/ドロップと Rust の準備を含む、読み込みとレポートのシリアル化を除く、完全な実行の中央値です。比率は、最新の中央値を共有セッションの中央値で割ったものです。

準備キャッシュは無効のままでした。したがって、`Reused / input tokens` は、トークン化キャッシュのヒットではなく、実際の ネイティブ プレフィックスの再利用を指します。

モデルごとの 210 ペアの 判断 比較、生の候補 logits、候補間の相対 の確率、候補の確率質量、選択された値、および 判断保留 の理由が正確に一致しました。レポート JSON には、ラウンドごとのタイミング、再利用されたトークン数、モデル/ランタイム ハッシュ、数値の差分 ([Qwen3](../../../../benchmarks/shared-state-cache-20260925/qwen3-0.6b-sm86.json)、[Gemma 4](../../../../benchmarks/shared-state-cache-20260925/gemma4-e2b-sm86.json)) が保持されます。ベンチマーク ソースは [`examples/benchmark_shared_state_cache.rs`](../../../../examples/benchmark_shared_state_cache.rs) です。

観察されたゲインは、変更されていない状態に関するいくつかの質問に対するプレフィックスの保持をサポートしています。単一の質問には再利用がなく、測定されたメリットもありません。これは明示的なインプロセス セッションであり、自動クロスリクエスト LRU ではありません。HTTP 解析、キャッシュ ルックアップ、エビクション、複数の保持された状態とそれらのメモリ コストは測定されませんでした。合成ワークロードには品質ラベルがなく、本番環境 レイテンシーまたは 正解率 が確立されません。 5 つのラウンドは、このホストとワークロードのみを特徴づけます。

<a id="architecture-specific-build-check"></a>
## アーキテクチャ固有のビルド チェック

`scripts/build_cuda_arch.sh 86` は、ネットワーク フェッチを回避するために既存のローカル llama.cpp ソース チェックアウトを使用して、別の `target/cuda-architectures/sm_86/` Cargo ターゲット ディレクトリで完了しました。その CUDA コンパイル フラグには、`compute_86` と `sm_86` のみが含まれていました。スクリプトは、一致する ネイティブ ライブラリを実行可能ファイルの横にコピーし、`release/run-l2s1` を作成しました。そのランチャーは、RTX 3080 上で 3 つの 判断 スモーク リクエストを完了しました。ローカルの ネイティブ ログは、29/29 モデル レイヤーが CUDA にオフロードされたことを確認します。 [ビルドログ](../../../../benchmarks/shared-state-cache-20260925/build-sm86.log)および[スモークレスポンス](../../../../benchmarks/shared-state-cache-20260925/sm86-smoke.json)を参照してください。反復的な ネイティブ ログは無視されたローカル結果に残ります。他の CUDA アーキテクチャは、このチェックではコンパイルまたは実行されませんでした。

<a id="rebuild-on-the-pr-branch"></a>
## PR ブランチで再構築する

コミット `0260180a5c950981cb642a3235b750529b7e4c3a` も、クリーンな PR ワークツリーから `scripts/build_cuda_arch.sh 86` を使用して構築されました。リリースのビルドは、完全なローカル llama.cpp ソース キャッシュを使用して、17 分で完了しました。その CUDA フラグは、`compute_86` および `sm_86` のみをターゲットにしていました。ランチャーは、一致する ネイティブ ライブラリを使用して作成されました。新しい 3 つの 判断 Qwen3 0.6B スモーク リクエストが RTX 3080 上で完了し、29/29 モデル レイヤーがオフロードされました。 [再構築証拠](../../../../benchmarks/shared-state-cache-20260925/pr28-sm86-rebuild.json)には、バイナリ、ネイティブライブラリ、ローカルログハッシュ、フラグ、スコープが含まれています。 [smoke レスポンス](../../../../benchmarks/shared-state-cache-20260925/pr28-sm86-smoke.json) には、バックエンド デバイスと判断が含まれます。上記の共有状態タイミング テーブルは、このコミットでは再測定されませんでした。
