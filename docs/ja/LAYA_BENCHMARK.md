# Laya/Jev タスク アダプターとキャッシュの評価

[English](../en/LAYA_BENCHMARK.md) · [한국어](../ko/LAYA_BENCHMARK.md) · [日本語](LAYA_BENCHMARK.md)

[English index](../en/README.md) · [한국어 색인](../ko/README.md) · [日本語索引](README.md)

Rust `l2s1-tools laya-benchmark` コマンドは、ローカル L2S1 JSONL エバリュエーターを使用して、[Luni/laya-jev-benchmark](https://huggingface.co/datasets/Luni/laya-jev-benchmark) によって使用されるパブリック タスクを評価します。 Laya のロード、評価ラベルでのトレーニング、または個別の JevBench 複合スコアの生成は行いません。

| 評価セット | 固定評価データ | 範囲 |
| --- | --- | --- |
| `phish` | `AreLit/PhishNChips`, `core_emails.csv` | 2,000 emails, balanced binary labels |
| `typed` | `LocalLLaMA/typed-decisions`, `all/test` | 400 cases, 2,000 binary/choice/ordinal decisions |
| `probes` | Luni の文字通りのプローブ定義 | 9 つのリクエスト、 14 のユニークな質問: 接地、矛盾、配線のバリアント |

データセットとベンチマークのリビジョンはアダプターに固定されます。レコードのソース URL とファイルの SHA256 値を取得します。プローブ ケースは、固定された `probe.py` のフリーズされたレンダリングです。準備では SHA256 がチェックされ、ダウンロードされたコードは実行されません。データセットと生成された証拠は、ソース パッケージではなく、無視された `results/` に属します。ソース データセットは独自の条件を保持します。モデル チェックポイント はダウンロードされません。

<a id="prepare-and-run"></a>
## 準備して実行する

アダプターとスコアは Rust です。 Typed Parquet の準備では、Rust Apache Parquet リーダーを使用します。これらのコマンドには、Python および `pyarrow` は必要ありません。

```sh
cargo build --release --locked -p l2s1-tools
target/release/l2s1-tools laya-benchmark fetch --suite typed --output results/laya/typed-source
target/release/l2s1-tools laya-benchmark prepare --suite typed \
  --source results/laya/typed-source --output results/laya/typed

cargo build --release --locked --features llama-cuda --example evaluate_jsonl
target/release/l2s1-tools laya-benchmark run \
  --prepared results/laya/typed --output results/laya/fresh \
  --evaluator target/release/examples/evaluate_jsonl --model /path/to/model.gguf
```

同じフェッチ/準備フローで `phish` または `probes` を使用します。 CUDA の場合、`--features llama-cuda` を使用してエバリュエーターを構築し、`--cuda` と、`--gpu-layers 24 --model-load-mode read` などの チェックポイント に必要な配置を指定します。 `llama` 機能は、CPU 専用のランタイムを構築します。 [ビルド ガイド](GUIDE.md#build)を参照してください。小規模な統合チェックでは `prepare --limit 4` を使用できます。そのマニフェストとレポートは、結果をサブセットとして明示的にマークします。

各 JSONL ケースには、1 つの状態に関するすべての判断が含まれます。評価者は各質問を個別のリクエストに強制することはなくなりました。ケース ID、状態、質問指示、および 判断基準 のみが推論に入ります。ゴールド ラベル、ディストリビューション、ワークフロー タグ、根拠は別のファイルに保存されます。オプションの順序、バイナリ極性、および 順序付き レベルは保持されます。エンジンのデフォルトは従来のプロンプト、新規実行、無効化された準備キャッシュのままです。

すべての実行で、評価者/モデル/入力ハッシュ、コマンド、バックエンド 設定、すべての予測、エラー、タイミング、および準備キャッシュ カウンターのスナップショットが記録されます。欠落、重複、予期しない出力、切り捨てられた出力、または不正な形式の出力は、静かに 正解率 を改善することはできません。全体的な 正解率 は、計画された分母に対して欠落/失敗したラベル付き判断をカウントします。有効専用の 正解率 は別途命名されます。失敗した実行は証拠を保持し、失敗して終了します。

<a id="scoring-boundaries"></a>
## 得点の境界線

- `accuracy` / `raw_top1_accuracy` は、判断保留 より前の、すべての計画されたラベル付き判断で除算された未加工の正しい値です。 `valid_accuracy` は失敗した判断を除外し、その分母を置き換えてはなりません。 `accepted_accuracy` は、アップストリームの生の argmax タイ ルールではなく、実際の ネイティブ で選択された回答をスコアリングします。 `correct_accepted`、`wrong_accepted`、`coverage` (承認済み/すべて) と `accepted_correct_all` (承認済み/すべて) は別個です。結果には、計画分母を持つ `by_type` (`binary`/`choice`/`ordinal`) と `by_workflow` の両方が含まれます。
- バイナリ タイでは、アップストリームの `p_true >= 0.5` ルールが使用されます。 Choice/順序付き タイは、元のオプションの順序を使用します。 ネイティブ の受け入れは引き続きエンジン ポリシーに従います。
- フィッシングは、タイアウェア AUROC、リコール、プレシジョン、およびハードラベル Brier を報告します。上流の手書きの AUROC ランクは任意に同順位になります。このアダプターは代わりにネクタイの半分のクレジットを与えます。
- 入力されたタスクはハード 正解率、バイナリおよび選択肢の質問についてはソフト ターゲット Brier/TVD/KL/ソフト 正解率、順序付き の質問については予想レベルの MAE/1 以内をレポートします。丸められたソフト ターゲットは正規化されます。ハードラベル Brier は分離されており、クラスごとの平均ではなく、ラベル全体の合計が使用されます。 `nll_hard` は、ハード ゴールド ラベルに対する自然対数損失であり、有効なラベル付きの判断を平均し、確率は `1e-12` (最大 27.631 nats) に抑えられます。これには 順序付き ラベルが含まれており、ソフトゴールド KL またはソフトターゲット クロス エントロピーではありません。
- `ece_hard` は、argmax の正確性に対して 10 個の等しい幅のビンを使用します。これは、ソフト教師の分布との一致を測定するものではなく、不特定の上流の ECE 実装と互換性があるとは想定されていません。 `ece_hard_15` はさらに、15 個のビンを含む同じ定義をレポートします。信頼度は最大の候補確率であり、エントロピーの信頼度ではありません。どちらも有効なラベル付き判断のみを使用し、正確なビン エッジを上部ビンに配置し、確率 1 が最終ビンに配置されます。
- プローブの失敗はチェックごとに報告されます。補完テストと安定性テストはヒューリスティックです。一部のペアの質問は厳密な論理補完ではなく、ルーティングのバリエーションによってルーブリックの表現も変更されます。接地出力は、L2S1 エントロピー信頼度を明示的に使用する過信頼度チェックに再利用されます。普遍的な「11-test 正解率」や教師の合意の上限は推論されません。
- ソースによって公開された GPU 5090 のタイミングは、ローカルの CPU/3060 の実行と直接比較できません。ケースごとの待ち時間には、すべての質問と完全なバッチ完了が含まれます。質問またはバッチ サイズで分割すると、待ち時間ではなく、償却された作業量になります。

<a id="compare-caching-without-changing-the-task"></a>
## タスクを変更せずにキャッシュを比較する

即時リピートはキャッシュ診断にのみ使用します。リピートゼロは高品質の結果です。その後の繰り返しは、追加の独立した例としてカウントされることはありません。

```sh
target/release/l2s1-tools laya-benchmark prepare --suite typed \
  --source results/laya/typed-source --output results/laya/cache-input \
  --limit 4 --repeats 2

target/release/l2s1-tools laya-benchmark run \
  --prepared results/laya/cache-input --output results/laya/state-fresh \
  --evaluator target/release/examples/evaluate_jsonl --model /path/to/model.gguf \
  --prompt-layout state-first --execution-mode fresh --batch 64 \
  --cache-bytes 67108864

target/release/l2s1-tools laya-benchmark run \
  --prepared results/laya/cache-input --output results/laya/state-reuse \
  --evaluator target/release/examples/evaluate_jsonl --model /path/to/model.gguf \
  --prompt-layout state-first --execution-mode prefix-reuse --batch 64 \
  --cache-bytes 67108864

target/release/l2s1-tools laya-benchmark compare --prepared results/laya/cache-input \
  --baseline results/laya/state-fresh --candidate results/laya/state-reuse \
  --output results/laya/cache-comparison.json
```

比較には、同一の チェックポイント、評価者、入力、プロンプト ID、コンピューティング設定、およびポリシーが必要です。すべての確率、候補の確率質量、生のトップ選択肢、および受け入れられた選択肢をチェックします。レイアウトまたはバッチ サイズを変更するには、独自の新しいベースラインが必要です。これはキャッシュのみの比較ではありません。 0.02 確率/質量回帰許容誤差は、最上位の選択の変更や受け入れられた選択を決して許すものではありません。正確な等価性も報告されます。ウォームアップには時間が設定されておらず、その準備エントリは測定前にクリアされます。 KV は、通常のリクエスト境界でもクリアされます。

<a id="why-a-cpu-workload-can-show-little-cache-benefit"></a>
## CPU ワークロードがキャッシュの利点をほとんど示さない理由

CPU を配置しても、KV の再利用は無効になりません。 ネイティブ 実装は、作業を CPU/GPU レイヤーにディスパッチする前に、正確なトークン プレフィックスを比較します。区別すべき 3 つの異なる種類の作業があります。

| 方式 | 削減した処理 | 現在の対応範囲 |
| --- | --- | --- |
| 準備キャッシュ | プロンプトのコンパイル/トークン化と回答境界マッピング | 正確な状態とプロンプト エントリの 判断。モデル/構成のスコープとバイト境界 |
| プレフィックス KV の再利用 | CPU レイヤーを含む共有入力トークンのトランスフォーマー状態の再計算 | リクエスト内の質問、または明示的な不変状態セッション |
| 結果のメモ化 | 推論全体 | このアダプタでは有効になっていません。別のワークロードを測定することになる |

256 のデフォルトの事前入力バッチでは、255 トークンの共通プレフィックスにより、**zero** トークンが節約されます。再利用は、数値的な動作を維持するために、完全な元のバッチに切り捨てられます。最後のトークンは常に評価されます。したがって、リクエストごとに 1 つの質問、通常の個別の呼び出し、従来の命令優先レイアウト、変更された初期トークン、またはサポートされていないリカレント/ハイブリッド メモリにより、再利用がゼロになる可能性があります。準備のヒットだけでは、変圧器の作業が回避されたことを示しません。キャッシュ ヒット数だけでなく、`reused_prefix_tokens` と `native_ms` を検査します。

9 月の CPU 統合チェックでは、24、 2026 で、i5-12600KF 上の SmolLM2 135M Q8_0、4 つのスレッド、状態優先プロンプト、最初の 2 つの型指定されたテスト ケース (それぞれ 5 つの判断)、および 1 つの即時繰り返しを使用しました。バッチ 256 では、準備キャッシュにより準備が 16.45 から 7.93 ms に減少しましたが、合計推論は 3.4秒 付近に留まり、KV の再利用はゼロでした。バッチ 64 では、フレッシュとプレフィックスの再利用には 3.899 対 2.389秒 (1.63x) がかかり、2,048 トークンが再利用されました。すべての 20 確率ベクトル、候補質量、上位の選択肢、および受け入れられた選択肢は、その同じバッチ比較内でまったく同じでした。この小さなシリアル チェックは、31B または 本番環境 の速度保証ではなく、CPU の再利用を示します。バッチ 64 も、新しいパスをバッチ 256 より遅くしました。

同じサーバーは、CPU/GPU 分割で Gemma 4 31B Q4_K_M もチェックしました (24 オフロード レイヤー、8 スレッド、読み取りロード)。同じ 2 つの型指定されたケースとその繰り返しでは、バッチ 64 の新規/再利用に 108.552/69.904秒 (1.55x) かかりました。バッチ 128 は 62.438/42.770秒かかりました (1.46x)。どちらの同一バッチ キャッシュ比較でも、すべての 20 確率ベクトル、候補質量、および選択が正確に保存されました。ただし、一致するバッチ 256 の新しいケースには 41.677秒かかりました。どちらの小さいバッチのキャッシュされた構成もそのベースラインを超えることはありません。バッチ サイズ全体での最大確率変化は 0.00165/0.00504 で、この小さなサンプルでは選択は変更されませんでした。バッチ 256 をデフォルトのままにしておきます。 CPU キャッシュの有効性は、プレフィル ジオメトリの変更後の純利益を意味するものではありません。すべての 15 統合構成 (350 判断 レコード (繰り返しを含む)) は、エラーや切り捨てなしで完了しました。これは、アダプターによって準備された 4,000 ラベル付きの判断に関する完全な推論ではなく、小規模な型指定/フィッシング サンプルと完全な動作プローブ セットをカバーします。

<a id="speed-work-in-priority-order"></a>
## 優先順位に従って仕事をスピードアップする

1. **1 つのモデルを常駐させ、ケース レベルのグループ化を保持します。** アダプターはこれを実行します。 API 呼び出し間で不変状態に関する質問を変更するには、`SharedStateSession` を使用します。通常のリクエストは分離されたままになります。
2. **同じレイアウトの新しいベースラインで状態を優先して測定します。** 質問固有のサフィックスの前に共有証拠を公開します。レイアウトを変更するとモデルの予測が変更される可能性があるため、オプトインのままになります。
3. **短い CPU 状態で小さなプレフィル バッチをテストします。** バッチ 64/128 は短いプレフィックスを再利用可能にしますが、行列乗算の効率も低下します。各サイズでフレッシュとキャッシュを比較します。バッチアライメントガードは取り外さないでください。
4. **繰り返し入力および固定スキーマには、制限された準備キャッシュを使用します。** 候補マッピングは変更された状態全体でヒットする可能性がありますが、正確なプロンプト エントリは失われます。 ネイティブ 推論が優勢な場合、トークン準備の節約だけでは総レイテンシーを大幅に変えることはできません。 `boundary_and_other_ms` も調べてください。これには、検証、リクエスト境界のクリア、およびフェーズ タイマー以外のその他の作業が含まれます。 ネイティブ `sd_clear` は、ホスト バッファーを含む KV バッファーをゼロにし、通常のバッチ/リクエスト境界で繰り返し呼び出すことができます。冗長なクリアを削除したり、物理的なゼロ化から論理リセットを分離したりすることは、分離/エラー回復テストを必要とするフォローアップの最適化です。このアダプターはこれらのセマンティクスを変更しません。
5. **実際のメモリ バジェットに基づいて並列幅を評価します。** スループットは向上しますが、KV メモリが増加し、数値結果が変わる可能性があります。すでに 12 GiB VRAM に近い 31B モデルでは、さらにオフロードされたレイヤーまたはシーケンスが失敗する可能性があります。 `--request-batch-size` 単独では、フレッシュ モードでは ネイティブ 並列処理は作成されません。
6. **GPU オフロードを増やす前に、コンテキスト割り当てを測定された入力長に一致させます。** 短い分類入力には、8,192 トークン KV バッファーが必要ない場合があります。明示的なコンテキストを小さくすると、より多くのレイヤーのために GPU メモリを解放でき、CPU の計算が削減されます。すべての入力と応答コードのプレフィックスを確認します。決して黙って切り捨てないでください。新しいコンテキストと配置の組み合わせで品質と割り当てを再確認します。
7. **明示的な固定スキーマ プレフィックス セッションを後の機能として検討してください。** 通常のクロスリクエスト KV の再利用はここでは実装されていません。このような API には、正確なトークン プレフィックス チェック、モデル/テンプレート/アダプターの ID、制限されたメモリ、明示的な所有権、およびエラーの無効化が必要です。これを回答キャッシュと混同したり、意味的に類似した入力に対してキャッシュされた回答を再利用したりしないでください。

読み込みの変更により、トランスの推論量ではなく、割り当てと起動 RSS が変更されます。 量子化、CPU スレッド数とレイヤーの配置は別の調整軸です。それぞれが独立してチェックされた品質ベースラインを保存する必要があります。 31B フォールバックを備えた小規模な第 1 段階モデル​​も推論ポリシーを変更するため、独自の 正解率/採用率 評価が必要になります。
