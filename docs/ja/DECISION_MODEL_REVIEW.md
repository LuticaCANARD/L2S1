# 決定モデルの構造レビュー — 2026-09-27

[English](../en/DECISION_MODEL_REVIEW.md) · [한국어](../ko/DECISION_MODEL_REVIEW.md) · [日本語](../ja/DECISION_MODEL_REVIEW.md)

[English index](../en/README.md) · [한국어 색인](../ko/README.md) · [日本語索引](../ja/README.md)

**L2S1 は移植可能で観察可能な決定ランタイムを提供するが、それだけでは学習済み決定モデルの精度・校正品質・計算コストを実現したとはいえない。** 指定された [5モデル比較](https://fornewchallenge.tistory.com/1593)を受けてレビューした。[Kev の一次資料](https://github.com/jaredpalmer/kev#highlights)にある決定向け学習とホールドアウト校正は設計上の参考になる。異なるプロジェクトの代表的な精度や速度比は、このランタイムの統制実験ではない。外部モデルのコードや重みは取り込んでいない。

## 問題と優先順位

| 優先度 | リポジトリの根拠 | 影響と次の改善 |
| --- | --- | --- |
| P0: 信頼度と運用エラー率の混同 | [DecisionPolicy と採点](../../src/decision.rs)は候補間 softmax、候補質量の下限、共通の二つの閾値を使う。[HTTP](../../src/http/contract.rs)は `target_error_rate` を `1 - rate` に変換し、既に `guaranteed: false` を返す。 | 名前は実装より強い契約を示唆する。明示的なスコア閾値を優先する。真のリスクポリシーにはモデル・タスクに結び付く成果物、独立した校正、ホールドアウトでのエラー率とカバレッジ評価が必要。温度校正は信頼度を変えるが argmax の誤答は直せない。 |
| P1: デコーダ計算の反復 | [LlamaBackend::decide](../../src/llama.rs) の既定 fresh モードは質問を個別に評価する。Parallel は独立シーケンスをバッチ化し、[共有状態セッション](../../src/llama/shared_state.rs)は明示的な寿命内で完全一致するトークンバッチを再利用する。 | 複数質問を一つのリクエストに入れても、状態エンコード一回にはならない。質問数 1/4/16/64 と短い・長い状態で p95 とメモリを測る。共有状態エンコーダと動的質問・候補ヘッドは別の学習バックエンド実験であり、既定モードの変更では実現できない。質問間の隔離を維持する。 |
| P1: 回答コードとトークナイザの結合 | [複数文字採点](../../src/llama/code_sequences.rs)は完全な継続経路を評価し、並列・状態復元・校正・出力ヘッドとの組み合わせを制限する。[意味確率混合](../../src/consensus.rs)は追加推論と候補質量による重み付けを使う。 | 候補数が多いほど追加の順伝播が必要。候補質量はコード経路や形式にも依存し、分布外入力の検出器ではない。順序混合は任意の緩和策であり順序不変性の証明ではない。意味 ID に基づく回答変更率、受理回答変更率、確率 TVD、総遅延を同時に測る。動的候補スコアモデルは代替案。 |
| P1: HTTP とワーカーのスケジューラ分離 | [HTTP serve](../../src/http.rs)は上限付きキューからローカルジョブを一つずつ実行する。[BackendWorker](../../src/worker.rs)の任意マイクロバッチとは別経路。`receiver.recv()` に推論期限はなく、ソケットのタイムアウトは待機・実行ジョブを取り消さない。 | 長いジョブが短いジョブを待たせ、クライアント切断後も計算が続く場合がある。受付とスケジューリングを統合し、期限切れの待機ジョブをネイティブ実行前に除外する。実行中キャンセルにはネイティブ対応が必要。同時負荷でキュー p95、公平性、メモリ、状態隔離を検証する。明示的バッチ API は独立 HTTP リクエストを自動的にまとめない。 |
| P1: 評価実装の不一致 | Rust Laya 採点は同率で最後の候補を選び、受理回答の正誤も実際の値ではなく argmax から計算していた。文書にある NLL、15区間 ECE、種類別指標も欠けていた。 | 今回修正し回帰テストを追加。公開済み全テスト集計は同じ値を再現した。Rust/Python 間の再発を防ぐため、版管理された共通指標契約とツール間フィクスチャが必要。 |
| P2: 専門化の根拠と汎化の根拠の違い | [学習準備](../../training/src/l2s1_training/prepare_jev_data.py)は完全一致する状態と ID を分離するが、近似重複や事前学習での露出は否定できないと明記。固定パイロットは既知の四つのワークフローを扱う。 | 一般的な決定品質を主張する前に、出典・ワークフロー単位のホールドアウト、韓国語、情報不足、敵対的状態の評価が必要。最終テストラベルは保持する。モデルが選んだ `DONE` にもアプリ側の観察可能な完了確認が必要。スキーマの妥当性はタスク成功を証明しない。 |

[現行出力ヘッド](../../src/output_head.rs)は固定候補の定義、指示、決定 ID に結び付く。専門分類器として有用だが、動的状態・行動対照学習ヘッドへの置き換えには学習目的、特徴抽出、サービング契約の変更が必要。このレビューでその構造を実装・検証したわけではない。

## 反映した改善

Laya 採点の元順序による同率処理と、実際に受理した回答の独立採点を修正した。`raw_top1_accuracy`、`correct_accepted`、`accepted_correct_all`、`nll_hard`、`ece_hard_15`、`by_type` を出力する。欠落・失敗したラベル付き決定も予定分母に残し、採点コード・入力のハッシュを記録する。

Laya と公開 JevBench に `risk_coverage` を追加した。最大候補確率で元の argmax を順位付けし、同じ確率の標本はまとめる。曲線と経験的エラー予算 1%、5%、10% での最大カバレッジを提供する。ネイティブの質量・同率ゲートを無視する独立診断であり、実際の受理指標と区別する。テストラベルから求めた閾値なので、配備ポリシーや統計的保証として使えない。受理ゼロ件のリスクは 0 ではなく null。Laya の反復ケースは別のキャッシュ診断回として扱う。

## 保存出力の再採点

既存の [typed-decisions 全テスト](TYPED_DECISIONS_BENCHMARK.md)で二つのモデルの計 4,000 決定を再採点した。不正な出力はなく、公開済みの正答数と受理集計をすべて再現した。9月26日の出力のオフライン再採点であり、新たな推論・学習・校正・速度測定や精度改善の証拠ではない。

Gemma 4 E2B は 2,000 件中 1,855 件を受理し、822 件が誤答だった（受理エラー率 44.31%）。テストラベルを見て最良の確率閾値を選んでも、経験的リスク <=5% で残せる最大数は 120/2,000（**6%**）で、120 件中 6 件が誤答。Qwen3 0.6B は 1,112 件を受理し 730 件が誤答（65.65%）。同じ診断で残せる数は 1/2,000（**0.05%**）だった。この結果は二つの未校正モデル・タスク設定に限られ、全 L2S1 モデルには一般化できない。教師ラベルは合成で、質問は状態を共有するため独立標本を仮定する不確実性保証も示していない。

簡潔な [再採点の証拠](../../benchmarks/decision-review-20260927/summary.json)に入力・採点ハッシュとエラー予算別件数を記録した。全曲線はローカルの `results/decision-review-20260927/` に生成する。モデルを読み込まずに再現できる。

```sh
cargo build --locked -p l2s1-tools
mkdir -p results/decision-review-20260927
target/debug/l2s1-tools laya-benchmark score \
  --prepared results/typed-decisions-20260926/prepared \
  --predictions results/typed-decisions-20260926/gemma4-e2b/predictions.jsonl \
  --output results/decision-review-20260927/gemma4-e2b.json
```

もう一つのモデルは `qwen3-06b` に変更する。生の推論ファイルは git 対象外のローカルファイルで、簡潔な証拠には含まれない。指標回帰テストとツールの clippy は合格。ランタイムのスケジューリング、学習済み動的ヘッド、配備用リスク校正は今後の開発課題として残る。

## Prefix reuseと提供されたM5 Max比較

ユーザー提供の測定は2026-09-27、M5 Max、128 GB、macOS 27.0 (26A428)、AC接続・High Powerの条件による。未コミットの`local/metal-all-benchmarks`ブランチでの外部ローカル結果であり、ここで再実行したり個別出力を監査した結果ではない。GGUF/MetalとMLXはエンジンだけでなく量子化とプロンプトも異なる。decision-rulesのp50は3判断を含むリクエスト単位、JevBenchは項目単位なので混同しない。

Gemma 4 26B-A4Bのdecision-rules fresh p50は506.0 ms、jvは166.6 msで3.04倍の差がある。一方JevBenchは153.1対193.4 msと順序が逆転する。llama.cpp自体に原因を帰す前にワークロード構造を調べる根拠になる。要約のprefix reuse適用時約1.5倍という値には詳細行、layout/batch設定、実際の再利用トークン数がない。規則の再読込コストが大きいという仮説には役立つが、その割合の証明にはならない。jv HTTPの0.313–0.457 msはjvの転送・解析コストであり、L2S1推論のオーバーヘッドではない。

ローカルコードで確認した問題はリクエストの寿命である。通常の`decide()`はprefix-reuseモードでもリクエスト前後にKVを消去する。既存の`shared_state()`はstateを固定して質問を変えるため、規則・選択肢を固定してstateを変える処理を表現できない。新しい[`shared_decision()`セッション](SEMIF_ALGORITHM.md#fixed-schema-sessions)はプロンプト、正解、閾値を変えずにその寿命を提供する。バッチ境界による再利用制限は維持する。このネイティブAPIがHTTPプール、スキーマルーティング、SDKのKVセッションを自動的に追加するわけではない。

速度と正確さは別の課題である。提供されたM5結果の26Bは合成規則36判断でraw top-1が100%だが、typed-decisions 2,000判断では67.5%である。coverage 95.7%、accepted accuracy 68.7%なら、受理した判断の31.3%が誤答になる。Prefix reuseでこのリスクは修復できない。小型モデルのエンジン間の精度差は、プロンプト・テンプレート、トークン、量子化、選択肢順序を統制して比較する必要がある。ユーザーの要望によりMLX実装は対象外とした。

[RTX 3080 JevBench 231問の検証](JEVBENCH.md#rtx3080-rerun-20260927)ではbatch 64の再利用は入力トークンの6.48–7.20%でした。同一batchの出力は保持しましたが、Qwen3 0.6B・Gemma 4 E2Bともbatch 256 freshより遅く、batch変更自体で一部のtop-1が変化しました。CPUルールフィクスチャの効果はワークロードに依存し、最適化にはbatch処理量と正解変化の確認も必要です。
